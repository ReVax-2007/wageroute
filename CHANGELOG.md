# Changelog

All notable changes to WageRoute are documented here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) with the sections this project actually needs (`Added`, `Changed`, `Fixed`, `Removed`, `Known gaps`), and the release version numbers come from [docs/RELEASING.md](docs/RELEASING.md#semver-policy).

> **Reading this file.** `package.json` only changes at release time, so commits between releases carry the *previous* version number. Inside an `## [Unreleased]` block, identify work by its commit or pull request, not by the app version. `Unreleased` means merged into `main` and shipped in no build yet — it is what the next installer contains.

## [Unreleased]

### Added

- **Older entries out of sight.** The spreadsheet's new **Show** box (last 30 days, 90 days, 12 months or everything, saved as a setting, default 90 days) hides older entries from the grid. A note says how many are hidden, with **Show everything** beside it. Nothing is deleted or archived, and every balance still counts the hidden entries. Pocket's entries list follows the same window, with **Show older**.
- **Privacy Policy and Terms of Use, in English and French** (`PRIVACY.md`, `PRIVACY.fr.md`, `TERMS.md`, `TERMS.fr.md`). They state that the app, Pocket and the website collect no personal information, name the third-party services that deliver WageRoute, name the person in charge under Quebec's Law 25, and set out the not-financial-advice notice, consumer-rights carve-out and Quebec governing law. Linked from the website footer and the README.
- **One SVG logo, everywhere it can be.** `build/icon.svg` redraws the WageRoute mark as a vector and is the source of every logo: the website (favicon, nav and footer, which had shown an older, different drawing), Pocket's favicon, welcome mark and manifest, and the desktop sidebar. `npm run icons` renders the macOS, Windows, Linux and phone-install PNG/ICNS/ICO files from it, which also removes the white corners the old app icon carried.

- **One-command installers.** `install.sh` (macOS and Linux) and `install.ps1` (Windows), served from the website: they pick the build for the system, verify it against the release's `SHA256SUMS`, install it (DMG into `/Applications`; `.deb`/`.rpm` through the package manager with the AppImage as fallback; the Setup installer silently per-user) and clear the quarantine or Mark-of-the-Web block. A CI job installs the real latest release with them on Ubuntu, macOS and Windows.

- **Fingerprint or face, and an opt-in PIN, as further ways into the same key** ([ADR 0031](docs/decisions/0031-a-fingerprint-is-one-more-way-in.md)). Custody is now a set of wraps of one 32-byte data key — keychain, passphrase, PIN, passkey — and any one opens it. Every wrap is proved before it is written, can be added or removed at any time, and renders its own *protects / does not stop / if you lose it* rows.
  - **Desktop, PIN:** digits only, at least six, sealed with scrypt at `N = 131 072` (four times the passphrase's memory). It may stand alone as a passphrase does, and before it is saved the card makes the owner confirm that anyone with a copy of the file can try every PIN offline.
  - **Desktop, fingerprint or face:** a WebAuthn PRF wrap through Electron's built-in WebAuthn, in a small window served on `http://localhost` from memory by `session.protocol.handle` (no port opened). Offered only on Windows (Windows Hello), and only written when a registration returns PRF output and a second assertion opens the wrap. macOS keeps keychain and passphrase (`app.configureWebAuthn` needs an Apple Team ID, which the project does not have); Linux has no biometric keystore. The unlock order is keychain → passkey → typed, and cancelling the fingerprint falls through to the passphrase or PIN prompt, which now names which of the two it wants.
  - **Phone:** the vault gains a v2 format — a random data key wrapped by the passphrase, a PIN (PBKDF2 at 2 000 000 rounds) and a passkey's PRF output (`rpId` is the page's own hostname). A v1 vault stays readable and becomes v2 only when a PIN or passkey is added, in one re-seal. On v2, changing the phrase is a rewrap. The locked screen gains **Use fingerprint or face**.
- **A passkey is never the only way in**, on either device: the key file and the vault marker refuse it, and every removal that would leave it alone is refused with a sentence that says why. On the phone, the passphrase stays while a passkey exists.

- **Split transfer** ([ADR 0033](docs/decisions/0033-a-split-transfer-is-ordinary-transfers-saved-together.md)). The Transfers screen's **Several accounts** mode sends one source to several accounts at once. It shows the total to move and the source's balance afterwards while typing, and saves every line as an ordinary transfer in one all-or-nothing write. An optional **Through** account records the hop through the bank the lump sum lands in first. Pocket gets the same thing as **Split** on its Accounts screen. No schema change.

### Changed

- **Transfers take a category** ([ADR 0032](docs/decisions/0032-a-typed-category-is-the-persons-label.md)). The Transfers screen has a Category box next to the description, with the ledger's categories suggested and new names accepted. A round-up or small sweep between accounts is now one labelled entry instead of a transfer plus a relabel. The category stays filled in between transfers, and the recent list shows it.
- **A transfer can no longer leave a credit card**, on either device. The Transfers screen leaves cards out of the **From account** list and disables the swap when the destination is a card. The entry dialog and Pocket's entry sheet refuse a card as the source, and both writers refuse it with the same sentence from `src/shared/writeRules.ts`. Paying a card, which is a transfer into it, works as before. Transfers already in a ledger are not touched, and neither are imports or merges.
- **A typed category is kept as typed** on both devices. `Round-up`, `Credit payment` and `Paycheck` are no longer renamed to `Transfer`, `Debt` and `Income`. The app's own sweep, card-payment and paycheck rows still go to those seeded categories, so they are unchanged. There is no schema change.

### Fixed

- A desktop transfer posted with a `categoryId` filed its receiving leg by the accompanying text instead of the id. Both legs now get the same resolved category.

### Known gaps

- Windows Hello and real handsets have not run any of this. The desktop ceremony window was driven in Electron 45 on macOS with a CDP virtual authenticator; the phone's passkey path is unit-tested with a stand-in ceremony. See ADR 0031 for what was measured and what was not.

## [1.3.0] - 2026-11-04

The release branch, cut from `main` at `1328135`. Database schema **8 → 10** (`SCHEMA_V9` and `SCHEMA_V10` ship for the first time here), backups write version **10** and accept **2–10**, `npm test` is **744 tests across seventy-three files**, lint is 218 files clean. This is the release that contains encryption at rest, sealed backups, the phone vault, Pocket's edit parity, the container shapes and the load watchdog — none of which is in `1.2.0`.

### Added

- **The ledger can be encrypted, and only you decide whether it is.** Settings gained an **Encryption at rest** card. *Encrypt my ledger* rewrites every page as ciphertext — `chacha20`, through the cipher driver the app now builds on — and *Turn encryption off* rewrites it back to plaintext from the same screen. Nothing is encrypted unless it is asked for: a default install stays readable, and the card says so in those words. The key is a 32-byte data key that is never written to disk in the clear; `ledger.key.json` appears beside the ledger (`0600`) holding only **wraps** of it, and the owner chooses who holds the key — **This computer** (Electron's `safeStorage`, so the keychain answers to the login, not to a fingerprint), a **passphrase** (scrypt `N=32768, r=8, p=1` then AES-256-GCM), or **both**, where either one alone opens it. The card renders the honesty table from `src/shared/encryption.ts` rather than sentences of its own: each option states what it protects against, what it does **not** stop, and how it can lock you out, and an option without all three is a build error. The dated copies in `backups/` follow the ledger, so from the moment you encrypt, they are encrypted too; a data-folder move carries the key file with the database. Both directions take a `VACUUM INTO` pre-copy first, record a `pending` marker, verify the result on a fresh connection including an `integrity_check`, delete the safety copy once it has, and restart the app — and `reconcilePending()` puts the ledger back the way it was if a crash lands in the middle. That transition has now run end to end in the **packaged** macOS app driven from the Settings screen — encrypted, relaunched into the unlock prompt, opened with the passphrase, moved to a data folder and back, decrypted to plaintext — with passphrase custody; a shipped build has still never written a **device** wrap, and no Windows or Linux artifact has held a keyed ledger. [ADR 0029](docs/decisions/0029-encryption-is-a-choice-on-the-disk-and-on-the-way-out.md) records the choice, and supersedes [ADR 0019](docs/decisions/0019-the-ledger-is-plaintext-at-rest.md); [ADR 0020](docs/decisions/0020-there-is-no-app-lock.md) now says why this is encryption and not a lock.
- **A locked ledger has no app.** The launch opens the ledger before it registers a single channel, so an encrypted one that has not been unlocked means no ledger window, no ledger IPC, and no half-open state where a renderer could ask for rows: only the unlock prompt exists (`?mode=unlock`), with a masked passphrase field and a show toggle. A wrong phrase is refused and nothing is written; the refusal is logged as `ledger-locked` with no phrase in it, and a launch that does open logs only how many tries the passphrase took (`ledger-unlocked`) — the number is useful after the fact, the phrases never are, and nothing is throttled or locked out because anyone holding the folder can test guesses offline at their own speed. A ciphertext ledger whose key file is gone is **refused before the file is opened**, and the dialog names both paths: the ledger it would not touch and the `ledger.key.json` it could not find, with the two ways back. A container or a headless machine has no keychain, so `deviceCustodyAvailable()` reports false and the *This computer* option is withheld with its reason stated instead of failing later.
- **The diagnostics report says whether the ledger is ciphertext.** *Copy diagnostics* from Settings → About now carries a `Ledger:` line beside the database path: `plaintext on disk`, `plaintext, with a leftover key file beside it` (what a crashed decrypt leaves), or `encrypted (chacha20), key held by this computer and a passphrase` — plus a note when a change never reported back, in the direction it stopped in. It is the difference between *WageRoute refused to open my file* and *my file is damaged*, which is otherwise invisible to anyone without a hex editor, and it is made only of booleans, a cipher name and a marker state. The formatting moved to `src/shared/diagnostics.ts` so it is a plain function with no window to test against, and a test refuses the report whenever a 24-character base64 or hex run survives path-stripping — no key, wrap or passphrase can ride into the text someone pastes into an issue.
- **Changing who holds the key touches no page.** The same screen lets you add the computer to a passphrase-held key, stop letting the computer open it, add or change a passphrase, and remove one — five actions that re-wrap the same 32 bytes and leave the ledger alone, so they are instant and repeatable, and custody can be revised as often as the owner likes. Removing the last of two ways in asks a danger confirmation first, because it is the one choice that can end in a permanent lockout: there is no reset, no escrow and no support path anywhere in the product. The passphrase rule lives in `passphraseProblem()` — at least 10 characters, with the reason said aloud (whoever has the file tests guesses offline, at their own speed) — and the field and the main process cannot disagree, because they call the same function.
- **A backup can be sealed, and both devices open it.** *Export full backup* now asks which file you want: plain JSON, readable by any spreadsheet, or the same contents **sealed under a passphrase** — `wageroute-envelope` v1, AES-256-GCM under a key stretched with PBKDF2-HMAC-SHA256 at 600 000 rounds (accepted between 100 000 and 2 000 000), 16-byte salt, 12-byte IV, 16-byte tag, written as `wageroute-backup-<stamp>-encrypted.json`. The only part in the clear is when it was exported. Importing a sealed file stops the wizard at a passphrase step and shows no rows until it opens; the phone reads and writes the identical envelope through WebCrypto, so a file sealed on the desktop opens there and the other way round. A transactions CSV is never sealed — it is a report, and ADR 0017 keeps it plaintext. A sealed file with a lost phrase is a puzzle with one piece missing, and an **encrypted `wageroute.db` will not open in the published 1.2.0** (plain SQLite refuses it as `SQLITE_NOTADB`): a plain JSON export is the only copy that survives a downgrade.
- **The phone can seal its own copy — when the page is allowed a cipher.** Data on the phone gained a **vault**: *Seal this phone's copy* puts its tables under a passphrase separate from the desktop's and from an export's, `wageroute-vault` v1 beside one sealed record in IndexedDB, with the key held only for the session and never extractable. *Close it now* shuts the copy between visits, and *Seal it* opens it again. One honest constraint governs all of it: `crypto.subtle` exists only in a secure context, so a page served over plain HTTP has **no cipher at all**. There the seal and lock buttons are disabled and a locked copy is not offered as a solution — `NO_CIPHER_HERE` names the cause in one sentence, and the destructive *Forget this phone's copy* is refused rather than half-working. Serve Pocket over HTTPS or from the machine it runs on.
- **The tests the encryption layer ships with.** Sixteen suites cover it: the custody table and the passphrase rule in `src/shared/encryption.test.ts`, the envelope contract in `src/shared/envelope.test.ts` and its node:crypto reader in `src/main/envelope.test.ts`, `db/ledger-key.test.ts` for the wraps, `db/encryption.test.ts` and `db/custody.test.ts` for the transition and its rollback, `db/device-round-trip.test.ts` for the keychain wrap, `db/unlock.test.ts` for the gate — including that a ciphertext ledger with no key file is refused by name and its bytes are left untouched, while a plaintext one with no key file still opens as plaintext — `db/export-roundtrip.test.ts` for a sealed file written and read back, `window-security.test.ts` for the unlock window, `src/shared/diagnostics.test.ts` for the report's wording and the key-shaped-string tripwire, and on the phone `lib/vault.test.ts`, `lib/vault-store.test.ts`, `lib/sealed-store.test.ts`, `components/vault-ui.test.ts` and `components/seal-ui.test.ts`, with `without-cipher.ts` used to prove the no-cipher page. `Settings.export.test.ts` and `ImportWizard.test.ts` cover the seal choice and its passphrase step, and `storage.test.ts` moves a keyed ledger to a data folder and reopens it there. `npm test` is now **744 tests across seventy-three files**.
- **A manual entry can name the bill or goal it settled.** **Add entry** now offers **Bill payment** and **Goal funding** with a picker for the record, so a bill paid outside the prompt — or funded by hand — is recorded against that bill or goal instead of as a plain expense. A bill payment closes the bill's reservation and stops its reminder; the ledger shows a small tag with the bill or goal name beside the description. The repository checks that the named record exists, belongs to the user and matches the kind, so a stale or foreign id cannot be attached; a bill-linked adjustment remains a note, not a payment.
- **The ledger keeps a copy of the last week by itself.** Once the schema is settled at launch, `backupDaily()` writes a `VACUUM INTO` copy named `daily-YYYY-MM-DD.db` under `backups/`, using the local calendar day so the file matches the clock the user reads. An existing copy for today is left alone, so five restarts cost one file; the newest seven are kept, and a backup failure is logged instead of stopping the app from opening. Settings → *Where your data lives* says where those copies sit.
- **A bill prompt asks when an older bill really left your account.** A prompt whose due date falls in an earlier month now shows a date field — starting on the due date, capped at today — and names the month the money will count in. The chosen date is the one written to the ledger, so a bill paid on the 2nd no longer has to be recorded in the previous month to be logged from the prompt.

- **The ledger can live in a folder you choose.** Settings → *Where your data lives* can point WageRoute at a NAS share, an external disk or a folder that Google Drive, Dropbox, OneDrive or iCloud syncs, so several computers read the same data. The choice is stored in `storage.json` outside the database; switching validates the folder, takes a dated safety copy, writes the pointer and restarts into the normal open path. A chosen folder opens with rollback journaling (`synchronous = FULL`, no mmap) instead of WAL, and `wageroute.lock` names the one computer allowed to write it. A second computer is told which machine holds the lock; a lock untouched for three minutes is treated as abandoned, and an app that loses its lock closes the database instead of overwriting the new owner. An unavailable folder stops the app with its path rather than falling back to the local copy. Moving back copies the external ledger over the local one after a `pre-return` safety copy. See [ADR 0022](docs/decisions/0022-the-ledger-can-live-in-a-folder-you-choose.md).
- **WageRoute Pocket, an installable phone view.** A second static app in `src/pocket` opens a WageRoute backup, stores it in the browser, and shows Safe to Spend, cash, total wealth, bills, goals, recent entries and the ledger. It installs from the browser and works offline; there is no server, account, upload or analytics. Every figure comes from the desktop's own shared money functions. The phone edits bills, goals and entries through the desktop's own validation and each change travels back to the computer in the next export; a full merge in both directions landed later in this release, so the phone is no longer an append-only pad. Replacing the file and *Forget this phone* both ask first and say what would be lost. [ADR 0023](docs/decisions/0023-the-phone-reads-a-backup-and-writes-only-entries.md) records the original boundary, [ADR 0024](docs/decisions/0024-two-copies-merge-by-time.md) the merge that replaced it and [ADR 0025](docs/decisions/0025-the-phone-writes-through-the-desktops-own-rules.md) the shared writer that followed.
- **The phone edits bills, goals and entries.** Bills, Goals and **Add** on the phone open real sheets now: add or edit a bill's name, amount, frequency, due day, category, paying account, funding strategy and — when the strategy is *Choose specific paycheck to fund* — which paycheck, plus autopay and the active switch; mark a bill paid, pause it, archive or delete it. Add or edit a goal's target, remaining date, priority, pace, funding accounts and deposit account, and archive or restore it. Add any kind of entry the desktop has — expense, income, transfer, bill payment, goal funding, investment, adjustment — and edit one, with the account and kind controls locked and explained whenever the row is a transfer leg or a round-up sweep. Every field uses the same `MoneyInput` and `Field` as the desktop dialogs, and a refusal stays on the sheet in the desktop's own words.
- **The phone edits accounts, cards and all.** **Accounts** is a sixth tab on the phone: total wealth, cash on hand, card debt and the room left on the cards, one row per account with its balance and a utilisation bar on each card, and a sheet carrying the facts the desktop's row shows — what is owed, the limit, what is available, the percentage used, APR, minimum payment, when the statement closes and the payment is due, what is due now and how long the balance takes to clear at the minimum. Add and edit reach the writers the phone already had: name, bank, type, starting balance, the purpose choices and the colour palette, and for a card its limit, rate, minimum, last statement balance and the two cycle days. The type is locked on an account that already exists, the opening balance is not editable there, and **Remove** asks the desktop's question with **Archive instead** offered between *Keep it* and the danger button, counting the entries the delete takes with the account. The whole form is read by one shared function, `validateAccountForm`, so the desktop dialog and the phone sheet parse the same text and name the same field when it is wrong; the dialog lost its private parsers and kept its behaviour. Categories need no screen on either device — a new one is typed into an entry, which creates it. Paychecks, allocations and settings remain desktop actions, and so does writing a paycheck's set-aside (the phone derives only whether it has been spent).
- **The phone can fix a balance and pay a card.** An account sheet on the phone now carries the two row actions the desktop has always had. **Adjust balance** asks *What changed?* from the reasons that account type can honestly carry, takes the new figure and a date, and — on a card with a limit — lets that figure be typed as amount owed, available credit or utilization percentage, previewing the owed, available and used figures before saving; a delta of zero says *"That balance is already correct"* and writes nothing. **Pay this card** lists the spendable accounts the desktop's dialog lists, prefills the whole debt, and posts the same paired transfer: cash leaves one account, the card balance falls, total wealth does not move. The maths behind both — the three credit answers, the target in signed cents, the direction rules and every refusal sentence — moved into one shared function, `resolveAdjustBalance`, and the desktop dialog was refactored onto it, so a typing cannot be read one way on the computer and another on the phone.
- **The phone settles a bill's set-aside itself.** A paycheck's reservation is a promise, and whether it has been kept follows from the payments in the ledger, so it has to be derived, not remembered. The desktop had derived it since ADR 0012 and the phone had never run the rule: paying a bill on the phone left its claim `reserved` — the bill still reading as owed — and deleting or halving that payment left it `paid` against a row that no longer existed. The walk now lives in one pure module, `src/shared/claims.ts`, with its ordering inside the rule rather than in whichever query remembered it; the desktop's repository reads rows and calls it, and the phone runs it after every entry write that pays, edits or destroys a payment, after an account delete, and over a file it has just merged. A claim moves only when the derivation disagrees with what is stored, so a device that has nothing to say leaves the other device's revision alone. [ADR 0028](docs/decisions/0028-both-devices-derive-a-bills-set-aside-from-its-payments.md) records it, and `src/pocket/lib/claims-parity.test.ts` drives the same money fact through the real desktop repository and the real phone writer to prove they agree. A cold review of that change then found its mirror image, and it was the worse of the two: the phone read a claim's due day from a key the **released** desktop never writes — 1.2.0 stops at schema 8, where a claim row has no `due_day` column — and a missing key read as day `0`, which opened the carry gate for every claim and settled last month's rent on the phone while the computer still held it reserved. Since a backup file is the only ledger a phone ever holds, that was the normal path rather than a corner. The phone now takes a claim's facts only where the computer's schema would have held the row and fills a missing due day from the bill, which is exactly what the desktop's own import does to the same row; a claim it cannot read is left as the file has it, and two rows sharing one id collapse to the one the merge keeps so a hand-edited file cannot make one promise collect money twice.
- **Both halves of the app run in a container.** `docker/pocket.Dockerfile` builds the phone app from the source in the build context and serves the folder from nginx: 77 MB, no Node and no toolchain in the runtime layer, with the headers a plain file drop cannot carry — `Content-Security-Policy: frame-ancestors 'none'` as a real header, `no-cache` on `index.html`, `sw.js` and the manifest so a new release lands on the next open, `immutable` on the hash-named assets, and `application/manifest+json` so Chrome still offers the install prompt. `docker/desktop.Dockerfile` runs the real Linux Electron build against Xvfb and streams that window out through x11vnc to noVNC on port 6080: the renderer talks to a preload bridge with no HTTP server behind it, so there is no browser build of the desktop to serve, and this is the desktop's own window watched over a websocket rather than a web app. It runs with `--no-sandbox`, one session per container, and `HOME=/data` so the ledger and the app's profile stay in a named volume. `docker-compose.yml` starts both, published to `127.0.0.1` only. `.github/workflows/docker.yml` builds and pushes both to ghcr.io — a version tag publishes `<version>` and `latest`, a manual run publishes `sha-<commit>` alone — through the runner's own docker CLI, so the workflow adds nothing to the supply chain beyond the pinned checkout; it has never run. The caveats, including why this is not a way to hand someone your ledger, are in [DEPLOYMENT.md](docs/DEPLOYMENT.md#running-wageroute-in-a-container).
- **TLS and a login can go in front of the containers, without either one entering the app.** `docker-compose.yml` gained an `edge` profile and `docker/edge.Caddyfile` the two site blocks it needs: Caddy terminates TLS with its own local CA and forward-authenticates every request before it proxies anything, then talks to **one person's** Pocket and desktop containers — which publish no ports at all, so the proxy is the only way in (measured from the Docker host; a second physical machine has not repeated the test). A second person is a second pair of containers with their own volume, not a second user row: [ADR 0030](docs/decisions/0030-self-hosting-puts-identity-at-the-edge.md) is the record of why the app has no login and never will. The example was validated and driven through a forward-auth stub — 401 with nothing proxied, 200 with a session cookie, both apps arriving over TLS whose chain verified against the CA extracted from the proxy's volume — and then run again with **two tenants at once**, where the isolation stopped being an argument: each tenant's container could not resolve or reach the other's in either direction, the two ledgers sat on separate volumes with separate inodes, the bundle served to both was byte-identical, and closing **Ann's** auth stub took both of Ann's hosts dark while **Bob's** kept serving with nothing new in Ann's app log. That second person costs about **205 MiB idle** (195 MiB desktop, 10 MiB Pocket) on an `arm64` Docker Desktop VM. And the default `docker compose up` is unchanged because everything new hides behind the profile. What it does **not** include: a real identity provider, a handset, or passkeys, because WebAuthn needs a registrable domain and a `.lan` name is not one. One trap belongs in the sentence: `docker compose down` skips services behind `profiles:`, so closing this shape means naming the profile again or the proxy keeps listening. The commands, the fail-closed list and the proof are in [docs/DEPLOYMENT.md](docs/DEPLOYMENT.md#tls-a-login-and-more-than-one-person).
- **`docs/POCKET.md`, the phone's own guide.** The repo could describe WageRoute Pocket but never told anyone how to use it. The new guide is task-shaped: what you need before starting, how to get it onto the phone, what the first run asks, what each of the six tabs shows and does, how to carry changes between the two devices and what last-write-wins means for your typing, what the phone deliberately refuses to touch, every refusal it can show and what to do about it, and a status section that keeps "proved by tests" apart from "never run on a real handset". `README.md` gained a five-step Pocket walkthrough and points here; `FEATURES.md`, `DEPLOYMENT.md`, `RELEASING.md` and `SECURITY.md` link it instead of restating it.
- **Every money field now behaves like money.** Bill, entry, goal, account, paycheck-card and adjustment amounts use one `MoneyInput`: digits, the first period, an on-screen decimal keypad, and no pasted letters or currency symbols. Typing keeps the separators already in the field, so `1,850` survives keystroke by keystroke instead of collapsing to `1.85`; leaving the field settles it on one exact form (`1850.00`), and an amount it cannot read is left exactly as typed. Percent fields use `PercentInput`, the allocator's income field, the spreadsheet's inline editor and the phone's input share the same rules, and a ledger entry still accepts a minus sign only at the start.
- **An adjustment says why it happened.** The adjust dialog offers a reason — mistake, rounding, interest earned or charged, investment gain or loss — and files the entry under a matching memo and category (`Interest earned` → Income, a gain or loss → Investing) instead of calling every correction the same. A gain must raise the balance and a loss must lower it, so a direction that contradicts the label is refused. Only reasons that make sense for the account are offered.
- **A credit card can be adjusted by what is owed, what is available, or how used it is.** The adjust form on a card offers **Amount owed**, **Available credit** and **Utilization**, resolves each to a target balance, and previews the amount owed, the credit still available and the utilisation percentage that saving will produce. Available credit and percent are clamped at zero, and a card without a limit only gets the amount itself.
- **The emergency fund can include a manual buffer.** Auto mode adds an optional cushion on top of months × essentials for the one-offs the monthly average misses. An empty, negative or non-numeric buffer adds nothing, and a buffer still counts when essentials are zero.
- **One-time income has its own section on the dashboard.** This month's non-paycheck income shows as a total and a list, with an **Add income** dialog that writes an `income` entry to a checking, savings or cash account. It is never treated as a paycheck and never enters routing.
- **A goal can be funded as fast as possible, paced to its target date, or paused.** Schema 10 adds `goals.funding_pace`. `by_date` caps each cheque at the amount needed per remaining pay period, so the goal still arrives on time without swallowing the whole routing; `paused` removes the goal from the allocator while keeping its target and progress. The goal dialog sets the pace, the card has a pause/resume button, and existing goals default to `asap`, which writes exactly the allocations v9 did. This is the number the release now carries: backups written by this build are version 10 and the reader accepts 2–10, so the version quoted in the schema-9 bullet below was that batch's own number, not the shipped one.

- **The window can open exactly one external page.** `setWindowOpenHandler` used to hand *any* `http(s)` URL to the system browser, which made it a general exfiltration path for a compromised renderer. It now consults `isAllowedExternalUrl()` in [`src/main/window-security.ts`](src/main/window-security.ts), which compares the exact origin and path and allows only `https://buymeacoffee.com/revax`; every other URL — including other `http(s)` hosts, `file:`, `javascript:` and lookalike hosts — is denied without opening. `will-navigate` and the IPC `isTrustedFrame()` gate now share one predicate, `isTrustedPageUrl()`: the packaged page by exact URL, or the dev server by origin during development. Both permission handlers now answer from one allowlist (`permissionAllowed()`) that permits only `clipboard-sanitized-write` — the copy buttons need it — and denies every other request and permission check.
- **A tag cannot build a tree that is not the release.** A tag-only `guard` job fails the workflow unless `${GITHUB_REF_NAME#v}` equals `package.json`'s version and the tagged commit is an ancestor of `origin/main`. The `release` job now refuses to replace assets on a release that is already published, so a re-run cannot invalidate a `SHA256SUMS` someone already kept.
- **`src/main/window-security.test.ts`, `src/renderer/src/lib/finance.test.ts` and the cases added across the existing suite.** The new suites pin the exact-URL trust check against lookalike prefixes and wrong ports, the external-link allowlist, the one permitted permission, and the money maths the dashboard relies on (cash on hand, credit clamps, fundable accounts, the monthly and per-cheque wall, goal totals, the four-slice routing breakdown, the upcoming-payment horizon, day ordinals). The rest cover non-ASCII category identity through a version-7 upgrade, a bank id landing once per account, a deleted-row id being importable again, the pre-upgrade predicate table, the reserve carry between months, and selector behaviour with no snapshot, with wealth versus pool, and with a bill paid from cash versus credit. The reserve suite also proves one payment closes one carry, a delete leaves another payment's claim paid, a third strategy switch reserves nothing more, a due-day edit does not rewrite an old carry, and a text-only entry relinks to the live category. The settlement cases prove a payment closes only the claims it fully covers, a card charge that closed a claim does not withhold the cash reserve again, a delete re-opens a pre-v9 carry that has no `settled_by` link, and a mid-month part payment is recovered by the cheques still to come. `PriorityWall.test.ts` mounts the wall in jsdom and pins the reserved-versus-paid chip, the separate month sums and the next-check figure. `npm test` is now **339 tests across thirty-nine files**.
- **Money, the restore merge and the import wizard, tested where they broke.** `src/renderer/src/screens/Allocator.test.ts` drives the screen in jsdom and proves it writes nothing when the split cannot be saved; new cases cover a restored category matching a live name, a credit-card bill payment on the Priority Wall, the v8 snapshot cutoff, a renamed category's bills, an impossible calendar date in the wizard, and a `Field` whose hint sits before a `<datalist>`.
- **A claim remembers how it was written, and which payment closed it.** Schema 9 adds `bill_reserves.strategy` and `bill_reserves.settled_by`. The plan receives the month's open claims instead of a list of reserved bill ids: a single-check bill subtracts every claim, an `all_checks` bill subtracts only a whole-month claim, so changing a bill's strategy between two cheques neither double-reserves the month nor loses the remainder already set aside. `settled_by` links a closed claim to the transaction that paid it, so deleting or moving that payment re-opens exactly that row; rows paid before v9 still fall back to the cycle lookup. Backups written by this build are version 9; versions 2–9 are accepted, and a restored claim without a stated strategy takes its bill's strategy.
- **The Home screen can use your name.** Settings now opens with a **Profile** card that stores the name the greeting uses. It is trimmed, capped at 60 characters and refuses line breaks so the greeting stays on one line; leaving it blank restores the plain **Good afternoon**. The name lives in the local database like everything else and is carried by backups.
- **An import says when the file was written.** The wizard's review names the date the backup was exported on, so the file about to be merged can be checked against the one you meant to pick; a date in the future is labelled as one and read as today.

### Changed

- **The phone's shell now behaves like the desktop's in three small ways.** `src/pocket/styles.css` had no reduced-motion rule, so anyone who asks the OS to cut animation still got the sheet slide and the backdrop fade every time — the desktop's own `prefers-reduced-motion` block, copied, now ends both at the frame they were heading for. It also had a focus style only on `.input`, so tabbing through buttons, the six tabs and the colour swatches showed nothing at all; there is now the desktop's accent ring on every focused control, and the text field keeps its own border-and-glow instead of collecting a second ring on top. Third, `index.html` pinned one `theme-color` (`#080b11`) while the stylesheet follows the system into light mode, so a light-mode phone got a near-black browser bar over a white app — a second `theme-color` keyed on `media="(prefers-color-scheme: light)"` now matches the palette the page actually paints. In the desktop, the first-run card's two buttons moved out of an inline `style` and into `.empty-actions` beside the rest of the empty state's rules. The built phone shell was then measured in Chromium: the focused first-run button computes `outline: solid 2px rgb(10, 122, 84) offset 2px` — the accent token — while a focused `.input` computes `none`, so the ring is real and does not double up; the reduce-motion block and `::selection` were read back out of the parsed stylesheet, and in a light-mode page the `theme-color` resolves to the same `#f5f7fb` the body paints. No pixels were looked at and the reduce-motion query was never actually flipped — see Known gaps.
- **The SQLite driver is now the cipher fork.** `better-sqlite3` is gone and `better-sqlite3-multiple-ciphers` ^13.0.3 is the only database module in `package.json`; `src/main/db/connection.ts` imports it. Its binary is the fork's own **N-API prebuild** for the platform — the same `.node` loads under Node and under Electron, so nothing is compiled against an Electron ABI and an Electron bump does not invalidate it — and the `**/*.node` asar-unpack rule is what makes it loadable at all from inside the packaged app. `npmRebuild: true` and the `install-app-deps` postinstall stay in the scripts, where for this module they are a no-op that would still build from source on a platform with no prebuild. A keyed ledger is a different file format from a plaintext one, so any build that swaps the driver back — including a plain `npm i better-sqlite3` taken as an ABI fix — stops being able to open it at all. Third-party notices and the packaging docs name the fork.
- **Imports merge by record, in both directions.** A backup imported on the computer or opened on the phone now adds a row it does not have, replaces a row whose copy is newer (`updated_at`, then `revision`), and applies a newer tombstone as a delete. An older copy of a row leaves the local edit alone, and settings merge per key under the same rule. A stamp later than the file's own export time is read as that export time, so two devices opening the same file agree about which copy is newer, and a tombstone for a row a copy never held is stored too, so its id cannot be reused. This is what lets an edit or a deletion made in Pocket reach the desktop through the same file. The import toast now separates **updated** and **removed** from **added** and **already present**, and a category rename onto another live name is refused with a reason. There is still no replace mode and no conflict dialog: the newer edit wins and the rule is stated on screen. See [ADR 0024](docs/decisions/0024-two-copies-merge-by-time.md).
- **The phone keeps what it was told, not only what it added.** Opening another backup merges it into the copy on the phone instead of replacing that copy, so entries typed since the last import survive a desktop export. Any live entry can now be removed on the phone; the removal is stored as a tombstone, travels with the next export, and takes a transfer's other leg or a purchase's round-up with it. The Data screen lists any notes from the last merge.
- **The phone writes with the desktop's rules, not its own.** `src/shared/writeRules.ts` is a pure module — no Electron, no SQLite, no DOM — that owns every value range and refusal sentence a write can be answered with, and the desktop's repository helpers in `src/main/db/repo/common.ts` re-export from it instead of keeping their own copies. `src/pocket/lib/write.ts` imports the same module and mirrors each repository's behaviour rather than its SQL: the same columns, the same linked rows, the same cascades on pause and delete, the same refusal. A person who mistypes an amount on either device reads the same sentence, and a row the phone saved is one the desktop's merge accepts with no special case. See [ADR 0025](docs/decisions/0025-the-phone-writes-through-the-desktops-own-rules.md).
- **One delete sentence for both devices.** `src/shared/deletion.ts` owns the question a delete asks — the title, the body naming what else goes with the row, and the confirm button — and the desktop's bulk bar, the grid's row button and the phone's entry sheet all build it from the same function. The phone used to spell the same words out inline, which is exactly how two devices drift; its confirm button now pluralises with the count (*Delete 3*) the way the desktop's does. The module now holds all six destructive questions — entry, account, bill, goal, whole-ledger erase and phone forget — plus the one archive-versus-delete line the account question shows above them, which both devices had been typing by hand, so the account dialog, the bills wall, Goals, Settings and the phone's Accounts, Bills, Goals and Data sheets all take their question from one place. `account:entry-count` left the IPC contract with it: once the account dialog asked the counted delete instead, nothing read that channel, so the channel, its handler, its bridge method and its store action are gone.
- **Destructive taps on the phone ask first.** Deleting a bill, a goal or an entry now opens a question that uses the desktop's own confirmation wording — *Its payment history and this month's set-aside go with it…*, *The fund disappears for good…* — with **Keep it** as the safe answer and a refusal left on the question instead of dismissing it. `src/pocket/components/DeleteConfirm.tsx` is the one component for all three, and every sheet button is disabled while the write is in flight.

- **Pocket validates every row and opens offline from a cold cache.** An unknown account kind, frequency, reserve state or other enum is refused for a schema version the build knows instead of being silently replaced, and money must be a whole number in every version; the allowed sets are shared with the snapshot builder. The service worker's build now stamps its release and pre-caches the hashed bundles, so an offline open is not a blank page, and a failed storage open can recover instead of caching its rejection forever. Saves, imports and erases report what phone storage actually did: the "saved" notice waits for the write, a load that cannot open storage says so instead of looking empty, and deleting a desktop row is refused with an explanation because the additive export cannot carry a deletion.
- **Pocket reads bills on their real next date and sorts like the desktop.** A bill's due date now comes from the shared recurrence engine, so a stale `next_due_on` no longer hides a weekly bill, and accounts, bills, goals and categories use the same code-unit order as the desktop instead of `localeCompare`.
- **Reading a large import no longer freezes the window.** The file is still size-checked before anything is parsed, but the check and the read now run on the main process's async I/O instead of blocking it, so a multi-megabyte statement no longer stalls the interface while it loads.
- **The screens speak plain English.** Navigation, screen titles and dialogs now use everyday words instead of the product's internal shorthand: **Priority Wall** is **Bills**, **sinking funds** are **Goals**, **guilt-free money** is **Fun money**, **true surplus** is **Left to split**, and **safe to spend** is **Left to spend**. Button labels follow the job they do (`Set aside bills`, `Split what is left`), warnings are written as sentences, and the paycheck plan stores its saved lines as **Bill money** and **Fun money**. Screen ids, bucket keys and schema stay unchanged, so existing databases and backups read exactly as before.
- **The documented gates match the ones CI runs.** `CONTRIBUTING.md`, `README.md` and the pull-request template now include `npm run lint`; `docs/DEPLOYMENT.md` describes the `verify` job's packaging dry run and the build job's lint step. The `dist:linux` documentation no longer claims both architectures: the script builds the host architecture, and CI runs one job per architecture. `docs/RELEASING.md` now says a tag creates a **draft** release, records that DMG blockmaps are written locally but excluded from the uploaded artifact patterns, and no longer says there is no publish automation.
- **Stale claims across the reference docs.** Error notices now document the real behaviour (successes fade after 4.2 s, errors persist) and the existing crash log rather than "no logging subsystem"; clearing all data is documented as the in-app two-step erase with its safety copy; the migration history names which schema versions shipped in 1.0.x, 1.1.0 and 1.2.0; and the import ADR counts the ten tables a backup now covers.
- **The reference docs no longer describe a product that does not exist.** SELECTOR counts, the number of screen dialogs, the CSP's inline-style allowance, the transaction index order, how boolean and due-day settings parse, the uncapped reference import, which account kinds a deposit may come from, the lint gate's contents, the restored-category rule, the settings allowlist, the narrowed malformed-date exposure and the one-entry external URL allowlist now match the code.

### Fixed

- **A local build says it is one.** `npm run dist`, `dist:mac`, `dist:win`, `dist:linux` and the new `dist:local` go through `scripts/dist.mjs`, which stamps the version `-dev` (`1.3.1-dev`), so the sidebar, Settings → About and *Copy diagnostics* no longer show a hand-built app as the published release. CI's release build calls electron-builder directly and keeps the plain version; a release assembled by hand sets `WAGEROUTE_RELEASE=1`.
- **A short window no longer clips the sidebar.** The sidebar hid its overflow, so on a window shorter than its content the flex layout squeezed the version line and the wealth card until their text was cut off. It now scrolls instead, and its blocks keep their full height.
- **A window that opened and never filled is no longer silent.** Both of WageRoute's windows *are* the product, and until now nothing in the main process watched a document load at all: no `did-finish-load`, no `did-fail-load`, and the only renderer signal was `render-process-gone`, which fires when a renderer dies, not when a page never comes. So the empty unlock window Batch 57 saw twice — a frame listed with the right URL, holding a 39-byte `about:blank` — produced no log line, nothing for *Copy diagnostics*, no reload, and no message; the promise that a boot failure is visible was true in letter (there *was* a window) and false in substance. `src/main/window-load.ts` now watches both windows: it reloads the document twice and then says so — a `window-load` (or `unlock-prompt-load`) crash line, and for the main window an error dialog that states the ledger was not touched before quitting; for the prompt, closing the window, which the open that is waiting on it already reads as "no answer". The retry is a reload because reloading is the one thing that was actually seen to fix that window. Twelve seconds of nothing counts as a failure, since silence is the only signal an empty initial document gives; a sub-resource failure does not, and neither does a load this module's own retry replaced. Six cases in `src/main/window-load.test.ts` pin the limit against an injected clock, and every path was driven: a dev URL with nothing behind it produced two `[window-load]` notes and the crash line; a byte copy of a keyed ledger produced two `[unlock-prompt-load]` notes, the crash, and then the existing `ledger-locked` refusal with the ledger untouched; a server that answered 15 seconds late produced one retry note, a second request 16 ms later, no report, and a live app. **What this does not do is fix the stuck window** — its cause is still unclaimed in [docs/UNRELEASED.md](docs/UNRELEASED.md); what is fixed is that a screen that never arrives is now retried, logged, and ended instead of waiting forever.
- **A ledger that opened correctly stopped being logged as a crash.** Opening a keyed ledger with a passphrase wrote `[ledger-unlocked] Error: The ledger opened with a passphrase on try 1.` to `logs/main.log`, and **Copy diagnostics** put that line in the tail a bug report is built from — so a boot that worked looked like the thing that went wrong, and a support conversation started by reading a file full of `Error:`. `src/main/log.ts` now has two writers: `logCrash` keeps its `Error:` and indented stack for the failures it was always meant for, and `logNote` writes a plain line for something that *happened*. The try count is still recorded, and still never the phrase; an unreadable ledger that had to be rebuilt from its safety copy is still error-shaped, because that one did go wrong. The module took its first test file with the change, including the promise that a full or unwritable disk never makes the logger throw into a caller that is already failing.
- **A keyed ledger with no key file said nothing.** Moving or restoring only the `.db` — leaving `ledger.key.json` behind — used to hand the ciphertext file to SQLite as if it were plaintext. It answered `SQLITE_NOTADB`, that error reached the generic boot failure, and the app logged a crash and exited with **no dialog at all**: the person saw the icon disappear and read nothing about which file was the problem. `openLedgerKey()` now inspects the ledger's own first bytes when no key file is there (`src/main/db/unlock.ts`); a file that does not read as plain SQLite raises `MissingKeyFileError` before the driver is involved, and the boot handler in `src/main/index.ts` turns it into a dialog that names both paths and the two ways back. Neither file is opened or rewritten, and no key is invented. Because the same byte test also fails for a plaintext ledger whose header was wrecked, the message names both readings instead of asserting one — and a plaintext file with no key file still opens as the plaintext it is.
- **The phone's own instructions named a button that does not exist.** The welcome screen told you to choose *Export a backup* on the computer; the computer's Settings button says **Export full backup**, so the first step of the only path onto the phone could not be followed from the phone. The screen's copy and `FEATURES.md` now use the real label. The same pass corrected four documents that still said a bill's set-aside was written and read only on the computer — true until Batch 50, untrue after it — and three sentences in `ARCHITECTURE.md`, `UNRELEASED.md` and `DEVELOPMENT.md` that described the entry-edit refusal as checking amount and date when it also checks kind, or listed test cases by names the files do not use.
- **An entry edited on the phone now writes.** Every save from the phone's entry sheet closed, reported success and changed nothing. The sheet always sends the entry's category, and the writer patched the ledger and then replaced that result with the copy produced while resolving the category — a copy derived from the rows as they were *before* the edit. The category is now resolved first and the edit applied on top of it, the shape the transfer branch of the same function already used. A regression test drives the exact patch the sheet sends and pins the amount, the revision and the reopened claim.
- **A partial save stopped blanking the columns a sheet did not show.** A patch built with `undefined` for an absent field used to overwrite that column, so editing a goal's target on the phone cleared its target date and deposit account. `patchRow` now treats `undefined` as "leave this alone", the way the desktop's `updateRow` leaves a column out of its `SET` list.
- **An optional text field can be cleared again.** A value of only spaces was refused with "X is required", which made a row whose institution, note or category had been erased to a space unsavable on either device. `optionalText` now reads whitespace as no value, and `assertDueDay` keeps its own label so a statement day says **Statement day must be a whole number from 1 to 31** instead of borrowing "Due day".
- **The import review no longer promises an append-only backup.** Its last step read *Everything already in this app stays exactly as it is — the import only adds what is missing*, directly above a button that merges newer rows over the local ones and applies newer deletes. The sentence is now chosen by file kind: a backup states the newer-wins rule and that an unmentioned row is left untouched, while a statement import keeps the additive wording. The phone's merge confirmation also agreed its number with its pronoun (*1 entry was added on this phone. They stay*); singular and plural are separate sentences now.
- **The phone shows the day you lived, not the UTC day.** Pocket sliced a stored import or export timestamp with `toISOString()`, so an evening import in New York showed **Nov 3** on a **Nov 2** screen. A shared `localDateISO()` keeps a date-only value and derives the local calendar day for a timestamp; the Data and Home screens both use it, and the exported filename now takes the local day too.
- **The spreadsheet's amount cell settles a trailing comma.** Leaving the inline editor after `12,` cancelled the edit even though the dialogs accepted it; the grid now canonicalises first, and repeated keypresses (`12,,`) drop every trailing comma, not only the last.
- **A Pocket currency warning uses the right article.** "has a amount that is not a whole number" now reads "an amount", chosen from the field label.
- **A trailing decimal comma settles like a decimal point.** Leaving a field after `12,` kept `12,` while `12.` became `12.00`, so a decimal-comma typist ended with a value every form refused and no field-level reason. A trailing comma is now dropped before the value is read: `12,` → `12.00`, `1,850,` → `1850.00`. Text the parser still cannot read is left exactly as typed.
- **A percent field no longer reads a fraction as a thousandfold percent.** `sanitizePercentInput('0,125')` treated `,125` as thousands grouping and produced `0125`, so a 0.125% utilisation could resolve to 125% of the limit. A comma in a percent is always the decimal point now — `0,125` → `0.12`, `1,234` → `1.23` — still capped at two decimals.
- **Pocket settles a bill from the payments it received.** A card-paid bill read **Due** on the phone while the desktop's prompt treated it as settled, and a part payment read **Paid** even though the rest was still owed. The state now follows this month's gross payments against the bill amount: a card payment settles it while Safe to spend still holds the cash for the card, and a part payment lists under **Still to pay** as **Part paid** with the amount already taken.
- **Pocket's payment history applies the desktop's kind rule.** A bill-linked adjustment appeared in the phone's payment history even though the desktop counts only `bill_payment` and `expense` rows; both now apply the same filter.
- **The spreadsheet cannot retype a row into a bill or goal payment.** The grid has no picker for the record those kinds name, so a retyped row was labelled **Bill payment** without closing anything and the bill still prompted. The kind list now offers income, expense, investment and adjustment; an existing bill payment can still be changed away from its kind, and transfers were already refused.
- **Pocket's offline cache gets a new name when only the shell changes.** The build stamp hashed asset filenames, so an edited manifest or icon with unchanged JavaScript left the cache name and `sw.js` identical and installed phones kept the old shell. The stamp now hashes the bytes of the shell files as well as the assets.
- **A grouped amount keeps every digit while it is typed.** The sanitiser stripped commas before the field could be read, so typing `1,850` became `1.85` on the second keystroke and the user could lose two digits without noticing. Typing now preserves the separators it is given, and the field settles on one exact form when it is left (`1,850` → `1850.00`, `1.850,00` → `1850.00`); an unreadable string such as `1,23.45` is left as typed rather than silently rewritten. A keystroke-by-keystroke test pins both separators, and the same rule now applies in the allocator's income field and on the phone.
- **Deleting a bill refreshes the ledger and retypes its payments.** `bill:delete` returned only the bills and reserves parts, so the grid kept a payment linked to a bill that no longer existed; and a live `bill_payment` whose link was cleared kept a kind with no bill behind it. The delete now returns the transactions part, and the repository retypes a live `bill_payment` to `expense` while clearing `bill_id` — the money and its date are untouched.
- **A bill-linked adjustment is not a payment in the prompt history either.** The month query already read only `bill_payment` and `expense` rows, but `listBillPaymentsSince` counted an adjustment attached to a bill as a payment, so a note could mark a later month as paid. Both queries now apply the same rule.
- **Bulk-deleting a round-up purchase counts the sweep exactly once.** `deleteTransactions` added the twin of a transfer but ignored the round-up legs a purchase owns, so deleting just the purchase reported one row while three disappeared, and selecting the sweep legs counted their pair again on top of the twins already in the selection. It now gathers every transfer twin and round-up leg the batch can touch and returns the drop in live rows, so the confirmation matches what left the grid.
- **The phone claims every row its own form wrote.** A transfer posts two ledger rows and a purchase that rounds up posts three, but only the row the writer named was marked *on this phone*, so the other legs read as though they had arrived in a backup and the Data screen's "added here" count was short. Every row a write posts is now marked, and the count means entries rather than mixing in bills, goals and accounts. Deleting on the phone counts too: a rounded-up purchase asks *Delete 3 entries?* instead of promising one row and taking three.
- **The desktop's delete confirmation now counts what the delete really retires.** Its promise was the number of rows ticked, while the write that followed also took a transfer's matching leg and the two sweep rows a rounded-up purchase owns — so a $12.34 purchase that swept twice was confirmed as one row and removed three, and only the toast told the truth afterwards. The count now comes from the database, through a read-only channel that returns the same set `deleteTransactions` is about to remove; the grid's row button and its bulk bar both ask the counted question, so a purchase reads *Delete 3 entries?* with a **Delete 3** button on either device.
- **Deleting an account counts the rows that actually leave it.** The question read the entries recorded *in* the account while the write also retired a transfer's twin in another account and the sweep legs of a purchase made from it, so the dialog promised 3 and removed 5. The account delete now goes through the same doomed-row expansion as an entry delete — on both devices, which previously removed different sets from the same file — and the desktop's hand-written transfer walk is gone, so an account delete can no longer leave a live sweep row pointing at a purchase that is not there. The confirmation reads *Deleting removes the account and 5 entries from every total.* with a **Delete account and 5 entries** button, or admits it could not check when the read fails.
- **A bill question names both fates.** The summary that feeds the sentence called every linked row a *payment*, including adjustments, and the desktop asked with no numbers at all. It now reports `{ reserves, linkedEntries }` — what goes with the bill and what stays in the ledger having lost its link — read with the same filter the delete uses: *Its 2 set-asides go with it, and its 3 entries recorded against it stay in the ledger without the bill.*
- **The two whole-ledger questions say what they destroy.** *Erase all data* now lists the ledger entries, accounts, bills, goals and paychecks it empties, counted from the snapshot's true totals rather than the grid's 500-row window, and *Forget this phone* separates the entries living in that browser from the rows this phone wrote, and tells the person to export before forgetting — the phone cannot know which of those rows already reached the computer, so it no longer claims they never did.
- **A confirmation waits instead of guessing.** While the account dialog's count was still on its way it rendered the *could not check* sentence, which promises every linked row on the strength of nothing; it now reads *Counting what this removes…* with a disabled **Counting…** button and only names a number once the ledger has answered. The bill's fallback made the same mistake in the other direction — it asserted the bill has set-asides — and now reads *Any set-asides it has go with it, and any entries recorded against it stay in the ledger without it*, with no digit in it.
- **The phone stopped promising what it cannot know.** *Forget this phone* claimed the computer had never seen the rows its `localIds` set names, but that set only drops a row when it stops being live, so a row already carried to the desktop in a later export stays in it; the sentence now names the rows this phone wrote and tells the person to export first. The phone's account toast also named a count the desktop's toast does not, so the two devices ended the same delete with two different sentences; the number now belongs to the question, as it does on the desktop.
- **The phone saves only what the transaction committed.** `run()` resolved on the request's `onsuccess`, which fires before IndexedDB commits, so a write could look saved and vanish on reload. It now resolves on `transaction.oncomplete` and rejects on error or abort; a commit with no ledger throws instead of returning quietly.
- **The phone sorts like the desktop and shows how old its copy is.** Same-due-day bills used `localeCompare` (apple before Zebra) where SQLite's binary collation puts Zebra first, so the phone now sorts by code unit through one shared comparator. The Data screen also shows both when the file was received and when the desktop wrote it, instead of labelling a months-old backup as fresh.
- **The phone's service worker cannot delete another app's caches.** Its activate step removed every cache whose name was not its own, which on a shared origin would wipe unrelated data; it now deletes only names under `wageroute-pocket-` and uses `ignoreVary` for the navigation fallback. The build stamp no longer repeats the prefix inside the generated cache name.
- **The import review no longer lists an incomplete row twice.** A row the user did not fill in appeared under **Not imported** as though it had been deliberately left out, and again in the red alert. **Not imported** now lists only the rows the user chose to skip, and the alert names each incomplete row once and points back to **Missing info**.
- **The import wizard will not promise a row the database would then drop.** Repairs used to be judged only when the answers reached the main process, so a typed answer that failed validation looked accepted until the import quietly left its row out. The wizard now runs the same `validateFieldValue` rules as it goes, marks the field with the exact reason, and keeps **Import** disabled until every answer passes; the review counts the ones still wrong. Blank answers are unchanged: they stay visible as incomplete rows.
- **A file stamped in the future cannot outrank later edits.** A backup from a machine with a wrong clock (or a hand-edited one) could carry `created_at`, `updated_at` or `deleted_at` values decades ahead. A whole-row import kept them, so every later local edit looked older to a last-write-wins reader. Any stamp later than the file's own export time is now written as that export time, and an export date itself in the future is capped at the merge, so two devices opening the same file reach the same answer; a genuine past stamp is preserved because it is the file's own history. The rule applies to financial rows and to settings `updated_at`, and the review labels a future export date.
- **A comma-decimal amount from a bank file is no longer read as thousands.** Every comma was treated as grouping, so a European statement line of `12,50` became $1,250. `parseMoneyToCents` now reads a lone comma with one or two trailing digits as the decimal point, keeps three-digit groups as thousands, follows the rightmost separator when both appear (`1.234,56` → 123456), and refuses malformed grouping (`1,2345`, `1.23,45`) instead of guessing. The CSV, OFX and QIF importers all use it, and a European bank export test pins `12,50` and `2.500,00`.
- **A utilisation you type is percentage points, not cents.** The adjust dialog fed the typed number through the money parser, so `5` became 500 cents and a 5% entry printed as 500% of the limit ($25,000 owed on a $5,000 card) before saving. `parseUtilizationPercent` now accepts a bare 0–100 number with at most two decimals, and `owedCentsAtUtilization` resolves it to `round(limit × percent / 100)`. `credit.test.ts` covers the accepted forms (`5`, `42.5`, `0.25`) and the refused ones (blank, a trailing period, a percent sign, three decimals, a negative).
- **A bill autopay settled before any cheque still reads paid.** Autopay on the 1st posts the payment at launch, before the month's first cheque has claimed the bill, and the wall only knew paid from a settled claim — so Rent read with no chip while the Allocator correctly left it out as already covered. The wall now marks a month paid from its payments as well, counts those payments in the **paid** summary even when no claim exists, and, without a payday, subtracts them from the per-cheque figure so a fully paid bill shows $0.00 and **Nothing more due** instead of its average share.
- **Restoring a backup after an erase brings your settings back.** Importing into a profile with no accounts, bills, goals, cheques or entries now replaces the seeded defaults with the file's values, so currency, pay cadence, splits, round-up and emergency choices survive the documented erase-then-import recovery. A ledger that already has history still keeps its local settings, and a value identical to the seed is counted as skipped.
- **A merge cannot leave a live claim under a dead parent.** A reserve whose bill was deleted locally is reported (`its bill was deleted or is not in this file`) and left out instead of holding money no screen can show; a reserve whose funding cheque is a tombstone still imports, and the claim replay reads that cheque so its payment marks the claim paid rather than reserved.
- **An import never commits a half-replayed ledger.** Claim derivation now runs inside the merge transaction, so a failure during the replay rolls the whole import back instead of leaving some bills re-derived and others stale.
- **A reserve without a `state` is filled, not asked about.** `bill_reserves.state` has a schema default, so the wizard no longer asks for it and an unanswered claim is no longer dropped along with the money it represents; a value the ledger cannot store is still questioned.
- **The shipped example backup agrees with its own payment.** Its October rent claim is `paid` and names the payment that closed it, and a test now merges the example into a fresh ledger so the fixture cannot drift from the replay again.

- **A sinking fund no longer has to take paycheck money it does not need.** The allocator used to fund every eligible goal with as much of the goal slice as it could. Each goal now carries its own pace: **As fast as possible** (the old behaviour), **Spread until the target date** (only this cheque's share), or **Paused** (nothing at all). A paused or fully funded goal cannot lower the money routed to savings, investments or debt.

- **A quarterly or annual bill no longer stays reserved after it is paid.** Its single payment had to pass the monthly carry rule, which required the funding cheque to fall after the bill's due day, so a 1,200,000 annual payment closed one 100,000 slice and left eleven reading `reserved`. A smoothed bill now clears every earlier claim whose cheque had arrived.
- **The Priority Wall stops asking for money a bill no longer needs.** A covered bill shows $0.00 and **Nothing more due** instead of naming a check with nothing left to do, a paused bill shows $0.00 and **Paused**, and the amount, cadence and due day moved under the bill name so the table fits its card without horizontal scrolling. The allocator's breakdown leaves out zero lines and says how many bills are already covered.
- **A bill-linked adjustment is not a payment, and a future one cannot release a month early.** The month's payment query reads only `bill_payment` and `expense` rows and accepts an as-of day; `commitPaycheck` passes the cheque's own date, so a future-dated entry no longer lowers the wall in advance.
- **A refund cannot grow the wall.** The renderer clamps each bill's paid figure at zero, matching the repository, so a net-positive bill no longer increases what is withheld.
- **Deleted parents stop holding claims.** `claimsThisMonthFor` and `recordBillReserves` join live bills and cheques, the wall ignores claims whose bill is gone, and deleting an account replays the claims its payments used to keep open.
- **A partly paid bill no longer reads "Paid this month".** One payment can close one instalment while another claim stays reserved, but the wall's chip treated any paid row as a paid month, so money it was still setting aside looked settled. The chip now reads **Reserved** whenever any claim is open and **Paid** only when none is; the summary above the table still prints the reserved and paid sums separately.
- **The Priority Wall and the dashboard render valid table markup.** Both passed their own `<tbody>` to `DataTable`, which already supplies one, so the page contained a nested body and React logged a hydration error on every render. The screens now pass rows only.
- **A payment closes only the claims its own amount covers.** A partial payment marked every claim it could reach `paid`, so a $600 payment could close two $600 months of carry; a payment smaller than one claim could not close it at all, leaving a fully covered month reading `reserved`. Claim states are now derived by replaying the bill's payments in date order: each payment is offered to its own cycle first and then to the earlier carry, coverage accumulates, and a claim closes whole only when the money offered to it reaches its amount.
- **A bill paid in two instalments settles.** Two $600 payments now close one $1,200 claim and `settled_by` names the payment that finished it; the old matcher gave up on the first claim larger than a single payment, so the month stayed `reserved` forever and the wall printed reserved and paid money for the same bill.
- **A refund does not count as a payment.** A positive bill-linked row took `ABS()` at settlement and could mark a claim paid. It now takes coverage back from the most recent contribution, so a refunded month reads `reserved` again.
- **Deleting or moving one payment cannot disturb another payment's claim.** A linked v9 delete also ran the legacy cycle fallback, which could re-open an unrelated unlinked claim. The replay leaves the claim a live payment still covers `paid` and names that payment.
- **An empty claim no longer strands the carry.** A zero-cent claim stopped the oldest-first loop, so every eligible claim behind it stayed reserved even after the bill was paid; the replay ignores non-positive claims.
- **A fifth weekly or third biweekly cheque is counted when it is real.** The part-payment remainder used the guaranteed slot count, so a weekly cheque on the 22nd of a five-cheque month divided the remainder over one cheque instead of two and risked an all-or-nothing shortfall. With a payday anchor the actual series decides; without one the guaranteed fallback is unchanged.
- **A claim the month already paid no longer blocks the cash the plan still owes.** The cap that stops a month reserving the same obligation twice counted paid claims as well, so a card charge that closed the claim also hid the cash a later cheque still had to set aside. The cap now counts open claims only.
- **A payment in the middle of the month is recovered by the cheques still to come.** With a semimonthly or weekly schedule, a partial payment divided the remainder by a fixed count of cheques per month, so paying before the last cheque under-reserved the wall: 30,000 paid on a 90,000 bill with two cheques left reserved nothing useful. The remainder is now divided across the guaranteed cheques still to come, so the next cheque carries its share and the last cheque carries the rest.
- **Deleting a pre-v9 payment re-opens the claim it carried.** A row written before `settled_by` existed had no link, so deleting the payment that closed it left the earlier month `paid` forever; the delete fell back only to the same-cycle lookup. It now re-opens the earliest earlier-cycle claim whose funding cheque fell after its due day, the same rule that carried it.
- **A committed cheque cannot spend one payment twice, and a partial restore lands on the right state.** The commit backstop replays every bill's payments (`reconcileAllBillReserves`) instead of closing every carried claim with every payment in the cycle, and `mergeBackup` runs the same replay once, so an imported ledger or a merged backup whose claims and payments arrived separately agrees without a manual edit.
- **Deleting or moving a payment re-opens only what the ledger no longer covers.** The old pre-v9 fallback reopened every paid claim in the month and cleared another live payment's link; the replay now recomputes the bill from its remaining payments, so only the claim that lost its money re-opens.
- **Switching a bill's strategy more than once cannot over-reserve the month.** Every claim now reduces the month's need, a spread cheque tops the month up to its normal share instead of scaling, and `recordBillReserves` caps a month's claims at the bill's monthly equivalent. Switching `all_checks → last_check → all_checks` reserves nothing the third time.
- **Editing a bill's due day no longer rewrites an old carry.** Each claim stores the due day it was written against, so a 31 January cheque still funds a 1 February bill after the bill is changed to due on the 31st.
- **The Priority Wall subtracts what the month already paid and claimed.** "Reserved on the next check" now accounts for this month's cash payments and open claims, and "reserved this month" counts reserved claims only, with paid claims reported separately instead of inflated into the reserved total.
- **The Allocator preview withholds the same amount the commit does.** A bill paid from a credit card releases only `paid − credit` in the preview, matching the repository, instead of showing a priority figure the recorded paycheck would not use.
- **A restored category must be usable.** A nameless category is reported instead of stored blank, a name longer than 60 characters is refused, and an entry that names its category only by spelling is relinked to the live row's id and spelling.
- **A category is one row however its non-ASCII letters are cased.** SQLite's `lower()` folds ASCII only, while reports group by the locale-aware `categoryKey`; looking a category up with SQL `lower()` therefore created a second row for `CAFÉ` and split one category's total into two report lines. Category lookup and the v8 text backfill now compare `categoryKey` in JS and link each entry by id, so a version-7 upgrade puts `CAFÉ` and `Café` in one category and leaves no entry uncategorised.
- **A bill paid next month stops calling last month's claim "reserved" — without closing claims that were never spent.** A claim belonged to the cheque's month and was only closed by a payment in that same month; a bill funded on 31 January and paid on 1 February left January's row `reserved` forever. A payment in a later month now settles the earliest open earlier claim whose funding cheque fell **after** the bill's due day in its own cycle: a 31 January cheque funds a 1 February due date under any strategy, including a monthly `first_check`, while a mid-month cheque funds its own month. A payment dated before the new month's cheque settles the carry, not the new claim, because that cheque had not been received yet. A payment moved from March to April therefore leaves March `reserved`, and one payment closes at most one claim instead of an arbitrary number of older rows.
- **The goal funding-account picker no longer shows a stale selection.** After applying a change, the checklist could keep rendering the previous choice. The picker now follows the saved goal until the user touches it (`draftIds`), **Select all** is derived from the live list instead of a one-time flag, and unticking the second of two accounts keeps the list open rather than swapping it for a select mid-edit. A rejected save no longer clears the draft, so the ids the user just picked stay on screen.
- **Deleting an account is no longer blocked by a failed count.** If counting the account's entries failed, the dialog kept **Delete** disabled with no explanation; it now says the count could not be read, labels the button **Delete account and its entries**, and stays available.
- **The account dialog explains a refused credit limit or statement balance.** Negative values were already rejected by the repository; the form now marks the offending field with its own message instead of failing silently on save.
- **Focus lands somewhere real when the dialog's trigger is gone.** A dialog that removed its own opener now returns focus to `#main-content` rather than calling `.focus()` on a detached node.
- **A pre-upgrade copy is written only for a real upgrade.** `needsPreUpgradeBackup()` requires an existing database (`current > 0`) and a strictly older version, so a fresh file or an already-current one no longer produces a pointless `pre-upgrade-*-to-*-*.db`.
- **The tag guard can see the whole of `main`.** After a full-history checkout it re-fetched `origin/main` with `--depth=1`, which made the branch shallow and left `git merge-base --is-ancestor` unable to walk back to an older commit on `main` — so a correctly placed tag could be rejected. The fetch is now full.
- **A restored category that already exists reuses the local row.** Restoring a backup compared category names with SQL `lower()`, so a file carrying `CAFÉ` inserted a second row beside a local `Café`, and that file's entries linked to the new twin. The merge now compares `categoryKey` in JS, matches against every live category before inserting, counts the matched file row as skipped, and rewrites the imported transactions' `category_id` and `category` text to the local id and spelling.
- **A bill charged to a credit card no longer releases the Priority Wall.** `commitPaycheck` subtracted the full `paidCents` of this month's bill payments from the withheld total, but a credit-card charge increases the debt instead of taking cash out — the wall was released by money that had not moved. It now withholds `paid − credit`; reserve settlement still receives every paid bill, so the claim is closed as before.
- **The launch-day net-worth point ignores entries dated in the future.** The v8 snapshot backfill summed every live transaction for each account, including ones dated after the snapshot day, so a future-dated entry inflated today's history point. The backfill now stops at the current day.
- **Renaming a category follows into the bills that bill against it.** `updateCategory` rewrote transaction text but left `bills.category` on the old spelling, so the next autopay entry recreated it and the category split in two. Every live bill whose `categoryKey` matched the old name is updated in the same transaction.
- **The import wizard refuses a day that never existed.** Date repair used `Date.parse`, which rolls `2026-02-31` into March, so an impossible date passed the wizard and sorted the entry into a month it never happened in. It now requires an ISO calendar date via `isISODate` and asks about anything else.
- **The Allocator does not route a paycheck with a split it failed to save.** When `saveSettings` failed, the store rolled the split back but the screen still called `commitPaycheck`, recording a paycheck against a split the user was no longer looking at. Routing now stops with an error that says nothing was written.
- **A field's hint stays linked when a `<datalist>` follows its input.** `Field` treated its second child as the described control when no `aria-invalid` was needed, so an input followed by a datalist lost its `aria-describedby`. It now clones the first element child and leaves siblings untouched.
- **Changing a bill's funding strategy mid-month no longer misstates the wall.** The allocator decided whether a bill was already claimed by looking at the bill's *current* strategy, so switching a carried bill to every-check made the second cheque reserve it again, and switching a spread bill to one check lost the instalment already reserved. The claim's own stored strategy now decides: the first case reserves nothing new, the second reserves only the month's remainder.
- **A typed decimal comma is read as the decimal point, not stripped.** The money input removed every comma before the parser saw it, so typing `12,50` filled the field with `1250` and saved a hundredfold amount. The sanitiser now keeps a lone comma with one or two trailing digits as the decimal point (`12,50` → `12.50`), keeps a trailing comma as a pending point, and still reads `1.850,00` as `1850.00` and `1,234.56` as `1234.56`.
- **A refund is no longer counted as a payment.** Bill prompts took `Math.abs` of every bill-linked row, so an imported refund could silence a bill that was still owed. They now net the signed amounts and clamp at zero, so a full refund restores the prompt and a partial one reports the real net paid.
- **Editing a purchase removes the round-up it no longer earns.** The update patch now reports the sweep rows the write retired, so the ledger stops showing a transfer the database had already removed.
- **Bulk-deleting a transfer counts both legs.** The confirmation said one row was deleted when the twin was also removed; the count now includes the live rows in the transfer group.
- **Deleting a bill unlinks its live payments.** Their `bill_id` is cleared in the same transaction, so the ledger no longer holds rows a write path would refuse or show a join name for a deleted bill. The payments and their money are kept.
- **Retyping an entry drops a link its new kind cannot carry.** Changing a bill payment or goal funding to a kind that cannot hold that link now clears it, matching what the create path accepts; a bill payment retyped to an expense keeps its bill.
- **A full refresh cannot overwrite a newer edit.** `refresh()` now joins the renderer's write queue, so a snapshot read that started before a save can no longer land after it and replace the newer rows.
- **The clipboard error survives its own reload.** Settings showed "The clipboard refused the copy" and then cleared it while loading the diagnostics that make the details selectable. It now loads first and shows the message only when the details are on screen.
- **A small summary figure keeps its cents.** The compact formatter used one decimal at most, so the Accounts strip printed `$12.5` above a `$12.50` account. Amounts below $10,000 now print exactly; only larger headlines use compact notation.
- **Pocket opens offline with its scripts.** The service worker precached its assets from a request without an `Origin` header, while the browser requests the hashed script and stylesheet with `Vary: Origin`, so the cache lookup missed and the offline page loaded without them. Asset reads now ignore that variation, and a server-stopped reload renders the whole shell.

### Known gaps

The full list, with the evidence behind each line, is [docs/UNRELEASED.md](docs/UNRELEASED.md). These are the ones a release note should not hide:

- **Encryption has run end to end in a packaged build with one kind of custody.** The plain → keyed → plain transition, the unlock prompt, the missing-key dialog and the data-folder move were driven in the built macOS app with **passphrase** custody. A shipped build has never written a **device** (`safeStorage`) wrap, and no Windows or Linux artifact has held a keyed ledger at all.
- **The phone has never been a phone.** Pocket's screens were driven through the DevTools Protocol against the built shell; no real handset has installed it, opened it with the network off, or carried a file through its own share sheet. The container shape behind Caddy was driven against a forward-auth **stub** — no real identity provider has completed a login, and passkeys are unproven by construction because WebAuthn wants a registrable domain and a `.lan` name is not one. Two tenants have run side by side and their isolation was measured, but only on one `arm64` Docker VM, never from a second physical machine.
- **The empty window is watched, not fixed.** `src/main/window-load.ts` retries a document that never arrives, says so in the log, and stops instead of hanging — but the cause of the stuck frame Batch 57 saw is still unclaimed, and nothing here says it is gone.
- **Native dialogs cannot be driven.** A save or open picker is out of reach over CDP, so the import wizard's rendered flow and a sealed export's file naming stay hand checks.
- **No pixel and no screen reader has looked at any of this.** Capture is refused on the machine this was built on, so the appearance — this release's focus rings, its reduced-motion rule and its light-mode status bar — was **measured as computed values in Chromium** (parsed stylesheet, `getComputedStyle`, `:focus-visible`, the accessibility tree of the built phone shell) and never **seen** as an image. Nothing was read by assistive technology, no handset was involved, and the reduce-motion media query itself was never flipped: its declarations are proven present and parsed, their effect is proven only by reading them. Behaviour was observed; pixels were not.
- **The container publish has never run.** `.github/workflows/docker.yml` builds and pushes both images on a version tag, so this tag is its first real run, and the `amd64` images have never been started.

### Changed

- **The Safe-to-Spend meter measures the whole pool, not a hand-picked slice.** The dashboard's bar used to plot goal funding against tracked cash, which could sit at 0% while nearly all of the pool was spoken for. It now shows `pool − Safe to Spend` as a share of the pool, with an over-100% state ("more than you have") when the bills exceed the cash, and a dedicated note when no spendable cash is tracked at all.
- **Money routed to debt and investing leaves Safe to Spend until it actually moves.** The allocator's debt and investment allocations used to be labels only: the cash stayed in checking and Safe to Spend still offered it as free. `unsettledRoutingCents` now deducts those two buckets, less any positive entries on a credit or investment account since the earliest paycheque of the month, so the minutes a card payment or brokerage transfer lands the deduction goes away instead of charging the same dollar twice. Savings is not deducted — a savings account inside the pool is still spendable and one outside it was never in the pool. The dashboard prints **Routed to debt and investing, not yet moved** as its own line, and the Safe-to-Spend caption says routing records a plan rather than moving money.
- **The allocator says plainly what it does.** Step 3 states that a route records a plan against the deposit and that WageRoute does not move money between accounts or pay bills; the wall and the plan are one arithmetic, not a transfer, so the app no longer implies a movement it cannot make.
- **A goal funded by its own account is named as such.** When every goal's progress comes from a bound account, the plan now warns `goals_account_funded` with the overflow amount that falls through to savings, instead of the misleading `no_goals`.
- **Backups write version 8 and carry every table.** Version 7 added `bill_reserves`; schema 8 adds `categories` and `balance_snapshots` and the `category_id`/`external_id` columns on transactions, all of them in the importer's allowlist and the example backup. Versions 2–8 are accepted on import, and the export of settings keeps only keys the current build reads, so a restored file cannot carry a draft key that no longer does anything.
- **A save that fails keeps its dialog open.** Every mutation now returns whether it succeeded, and the account, bill, goal, entry and payment dialogs close only on success — a rejected save shows its error in place instead of dropping the form. Writes are serialised through one queue, so two fast saves cannot interleave their refreshes and land an older snapshot on screen. Settings save optimistically and roll back to the previous values if the write fails.
- **The CSV export is no longer capped at the newest 500 entries.** Export reads the whole ledger directly instead of re-using the screen snapshot, so an old year cannot silently fall out of a backup file. Both exports are written `0600`.
- **The dashboard no longer pays for screens it is not showing.** The spreadsheet (and its grid engine), the allocator and the import wizard are lazy chunks, and `react-data-grid`'s stylesheet loads with the grid instead of at app entry. The entry bundle drops from 1,005 kB to 793 kB, with the grid's 170 kB arriving only when the Spreadsheet is opened.
- **The local database is tuned for a read-mostly ledger.** `cache_size = -16000` (16 MiB), `temp_store = MEMORY` and a 256 MiB `mmap_size` replace SQLite's 2 MiB default cache and on-disk temporary sorts.
- **Bill prompting builds one payment index per call** instead of scanning every payment for every bill, so the cost is proportional to the ledger rather than to bills × payments on every render.

- **Backdrops close only on a click, not on a drag.** A dialog dismisses when the press *starts and ends* on the backdrop. Selecting text in a field and releasing the mouse outside the panel no longer throws the form away.
- **The light palette meets WCAG AA.** Muted labels, placeholders, faint captions and every bucket colour were darkened for the light theme, the accent green moved to `#0a7a54`, and `::selection` now uses the accent token pair instead of a fixed green that became unreadable on a light panel.
- **Long account and goal names stay inside their cell.** Account names in the ledger grid and the wall truncate with a tooltip instead of pushing the row, goal titles truncate in their card, and the wall table scrolls horizontally inside its own card at narrow window widths rather than clipping the action buttons.
- **The Accounts summary adapts to the window.** Four tiles sit on one row above 1180px and fold to a 2×2 grid below it, instead of squeezing into unreadable columns.
- **The import wizard's steps are labels, not mystery buttons.** A step chip is a button only when there is a step to go back to; the current step is a non-interactive `aria-current="step"` marker, and no chip reopens the native file picker.
- **Copy is specific where it was generic.** The spreadsheet's subtitle now describes the tab in front of you (editing the ledger vs a read-only 90-day forecast), the account-type hint says *"Leave as Nothing in particular to keep it a general account"*, and a failed route says the paycheck was not routed and nothing was saved.
- **Names are capped at 60 characters** in the account, bill and goal dialogs, so a paste cannot produce a row that no column can display.
- **The sidebar no longer flashes `v…`.** The footer reads `WageRoute` until `app:info` answers, then swaps in the version.
- **Exports are atomic and private.** A backup or CSV is written to a temporary file beside the target, flushed with `fsync` and renamed over it, so an interrupted export leaves the previous file intact instead of a truncated one that still looks like a backup. The ledger file itself is set to `0600` when it is opened.
- **"Erase all data" now erases.** Every connection runs `secure_delete = ON`, and the wipe ends with `VACUUM` and `wal_checkpoint(TRUNCATE)`. `DELETE` alone only marks pages free — the erased rows stayed readable in the file and the WAL with ordinary SQLite tooling. It now first writes a consistent `pre-erase-<timestamp>.db` copy under `backups/` (newest three kept, pruned separately from upgrade copies) and the confirmation dialog discloses it, so the one destructive action in the app has a way back without pretending the live ledger survived; once those copies rotate out, the erased rows are not recoverable from the live file or the WAL.
- **IPC answers only the app's own page.** Every handler checks the sender frame against the packaged `renderer/index.html` (or the dev origin) and refuses anything else, and `will-navigate` accepts exactly that URL instead of any `file://` path — a local HTML file that reached the window could otherwise inherit `window.api` and reset or read the ledger.
- **The packaged Content-Security-Policy is narrower than the development one.** The production build drops `'unsafe-inline'` from `script-src`, removes the localhost socket allowance, and adds `object-src`, `base-uri`, `form-action` and `frame-ancestors` restrictions. React Refresh and HMR keep the policy they need in development.
- **Autopay is described as what it does.** The bill dialog's hint says that, marked autopay, WageRoute records the payment dated the bill's due day the next time the app opens after that date, and that it does not move money between accounts — the wall clears itself instead of asking. (An earlier draft of this note said the app never posted a payment; that stopped being true when autopay shipped, and the hint now matches the code.)
- **Safe to Spend is measured in money you have, not money you will have.** The pool and the meter now sum `cashCents` — entries dated today or earlier — so a paycheck that is already recorded for next Friday no longer inflates what the dashboard calls spendable today. The account still shows its full ledger balance.
- **"Tight" means the paycheck is fully spoken for.** The allocator used to call a plan tight when the leisure bucket fell under 10% of income, which flagged a deliberate 100%-savings route and missed a plan whose bills exhausted the cheque but left a few dollars of leisure. It is now tight only when bills consume the whole deposit, and "covered" when anything at all is left over.
- **The emergency fund averages completed months only.** Counting the month in progress made `averageMonthlyVariableCents` swing with the day the screen was opened — one large purchase on the 1st read as a whole month, a quiet first week read as frugal. The window now ends at the last day of the previous month, divided by the months actually covered; the current month is used only until one month has completed.
- **Settings saves write only values the build knows.** `settings:save` round-trips the payload through `parseSettings` before writing, so a missing or malformed field falls back to its default instead of storing the string `undefined`; an unknown currency is still refused rather than replaced with USD.

Paying a salary into a credit card was never meaningful and is no longer offered.

- **Installer names are pinned.** `dmg.artifactName` produces `WageRoute-<version>-<arch>.dmg` and `nsis.artifactName` produces `WageRoute.Setup.<version>.exe` — one installer carrying both architectures — so no asset name has spaces to be rewritten by an upload.
- **Unused imports and parameters fail typecheck.** Both TypeScript projects now enable `noUnusedLocals` and `noUnusedParameters`.
- **The build records the npm version and the funding link uses GitHub's native field.** `packageManager` pins npm 11.20.0, and `.github/FUNDING.yml` uses `buy_me_a_coffee: revax`.
- **The documentation matches the code again.** `SECURITY.md`, `docs/SECURITY.md`, `ARCHITECTURE`, `DATA-MODEL`, `DEVELOPMENT`, `FEATURES`, `IMPORT-EXPORT`, `RELEASING`, `DEPLOYMENT`, `README`, `CONTRIBUTING`, the release-notes template and ADRs 0001/0005 were corrected for schema 7, the eight-table backup, the v7 migration recipe, the public repository, the 1.1.x support line, the real CI split (`verify` on Ubuntu; installers on a tag matrix), the new installer names, the pinned-version bump examples and the per-occurrence snooze. `RELEASING` also no longer claims that a newer database is opened without a guard.
- **A capped routing history says so.** `Snapshot.paycheckTotal` counts every routed check, and the dashboard's routing card reads *newest N of M routed checks loaded* when the 24-row snapshot is a slice, instead of presenting the slice as the whole history.
- **The import wizard sees every account, and holds one file.** `listImportChoices` no longer caps at 200 rows — a dropped account would be reported as unmapped — and only one preview is held at a time. Confirm now re-derives the questions against the live ledger and refuses when a new one appeared since the preview, rather than dropping the row it was never shown.
- **The CSV export is described as a review file, not a backup.** [docs/IMPORT-EXPORT.md](docs/IMPORT-EXPORT.md) now says every live transaction is exported and adds a **What a CSV does not carry** section — transfers are two rows and are refused on import, the currency is informational, every link between records is lost, and the JSON backup is the way to move data between profiles. Settings → Data repeats the short version.
- **Round-up switches itself off when its destination goes away.** Archiving or deleting the account a sweep points at now clears `roundUpEnabled` in the same transaction, so the switch can no longer sit disabled in the "on" position while nothing sweeps. Restoring the account leaves it off; re-enabling stays the user's choice.
- **A first run cannot leave half a profile.** The initial `users` row and its settings are now written in one transaction, so a crash between them cannot leave a profile that looks seeded and can never be completed. `data:reset` follows the boot rule as well: a development build returns to the demo profile, a packaged one to a blank ledger.
- **The last documentation corrections.** CONTRIBUTING now says `npm ci` and names the three checks honestly, DEVELOPMENT records twenty-one test files / 172 tests, RELEASING's schema and backup columns read 7, and ARCHITECTURE explains the legacy `cfr-` prefix kept for existing installations' theme and backup name.
- **A save returns the tables it touched, not the whole ledger.** Every write used to answer with a complete snapshot read, eight statements at a time, even when one row changed. A write now returns its value plus a `SnapshotPatch` holding only the affected tables, read inside the same transaction, and the renderer merges them into what it already has; the full snapshot is reserved for boot, an import and an explicit refresh. Saving an entry on a large ledger no longer re-sends every bill, goal and paycheck row over IPC.
- **The renderer is split by responsibility.** The Zustand store is now a thin join of a session slice (screen, allocator step, confirms, notices, snoozed prompts) and a data slice (queue, snapshot patches, every write), with the pure totals moved to `store/selectors.ts`. The seven screen dialogs live in `components/dialogs/`, the funding-account picker and the table shell are shared components, and every dialog's save state comes from one `useDialogSave` hook. Screens read the same `useFinanceStore` API as before, so no screen had to change its imports.
- **The stylesheet is loaded in cascade layers.** `app.css` is now an import list for `layers.css`, `base.css`, `components.css`, `screens.css` and `utilities.css`, making the intended precedence explicit instead of depending on where a rule happens to sit in a 3,000-line file. The react-data-grid theme moved into `styles/grid.css`, which the grid module imports; because the grid library ships its stylesheet unlayered, ours stays unlayered too and still wins on specificity. `Spreadsheet`'s lazy chunk carries that sheet, so no other screen downloads it.
- **The security and release documentation matches the code.** [docs/SECURITY.md](docs/SECURITY.md) now states schema 8 and the 2–8 backup window, the disclosed pre-erase copy, SHA-pinned actions, the lint/test/build gates, CI-generated `SHA256SUMS`, the generated notices and the Diagnostics/legal panels, and its CSV section no longer calls formula defusing an unfixed weakness. [docs/DEVELOPMENT.md](docs/DEVELOPMENT.md) documents `npm run lint`, `npm run notices`/`prebuild` and the measured `noUncheckedIndexedAccess` evaluation (122 errors, so it stays off for now). [docs/RELEASING.md](docs/RELEASING.md) describes the read-only build matrix, the separate release job, the draft release, `publish: null`, the pinned asset names and the two-stage ad-hoc signing. The root [SECURITY.md](SECURITY.md) no longer says schema 7.
- **Every paycheck picker follows the same rule.** The allocator's deposit list, the default-deposit list in Settings and the plan dialog now share `fundableAccounts` — live checking, savings and cash accounts. A bill's **Paid from** and the entry dialog stay wider on purpose, because a bill can be charged to a card and an entry can move money onto one; [docs/FEATURES.md](docs/FEATURES.md) states the distinction instead of leaving it to be discovered.
- **A duplicate deposit is caught by date and by a window, not only by an exact amount.** Any second paycheck into the same account on the same date is now refused, along with the same amount within three days either side, and the allocator's warning names which of the two it found so the confirmation is about the deposit that actually happened. **Route it anyway** still allows a genuine second deposit.
- **A ledger edit no longer re-reads the capped ledger.** Creating or editing an entry now returns the rows the write changed — the entry, its other transfer leg and any round-up sweep — plus the live entry total and this month's per-bill payments, and the store merges them into the snapshot in query order and drops whatever falls past 500. A grid save no longer sends up to 500 rows back over IPC or re-renders every screen from a fresh read.
- **Money hints and the wall's footnote use the settings currency.** The import wizard's money example (`Enter 12.34 for €12.34`) and the wall's annualised example are formatted with the chosen currency rather than a literal `$`, and a bill funded by one check reads **Reserved on the 2nd check of the month** (*each month* without an anchor) instead of **Nth check only**.
- **"Closest to the due date" follows the payday series the user actually has.** The option used a fixed day-of-month table, so a biweekly earner paid on the 2nd and 16th was told a bill due on the 14th belongs to the check on the 7th. `closestCheckIndexToDue` now takes the real series when the pay anchor and a check date are known, and the wall, the bill dialog and the reserve maths pass them; a fixed monthly payday still uses the table.
- **The import review counts a CSV name group by its lines.** Twelve entries sharing an unmapped account name were subtracted from the "Importing …" total as one, so the review promised eleven rows more than it would write; `ImportProblem` gained `lines` and leaving the group out subtracts all of them.
- **An unmapped CSV account starts blank.** The account question used to pre-select the first account in the ledger, so an unattended answer could post a whole group into an account the user never chose. Nothing is pre-selected now, and an unanswered group is left out and listed (a missing or bad date still starts at today, and the review prints it).
- **The import preview is spent when the import lands, not when confirm starts.** One preview is held at a time; it used to be retired before the write ran, so a failed confirm also consumed the token and the wizard's *"safe to try again"* copy was false. A produced result now retires it, and a throw leaves the preview standing.
- **The documentation describes these rules.** `FEATURES.md` states that `tight` means the paycheck is fully spoken for (a deliberate 100%-savings route is `covered`, replacing the retired 10%-leisure test), and `IMPORT-EXPORT.md` states the one-held-preview lifecycle, the blank account answer, line-based group counting, the alias-sign warning, the multi-account OFX refusal, the two-digit QIF year, and the uncapped CSV export beside the still-capped snapshot.

### Fixed

- **Impossible calendar dates are refused, not stored.** `isISODate` used to check only the `YYYY-MM-DD` shape, so `2026-02-31` and `2026-13-01` passed validation and were silently normalised by date arithmetic while the ledger kept the impossible string. It now round-trips through `Date.UTC` and compares the parts, and every write path that uses `assertDate` rejects the date with the same sentence the CSV importer already used.
- **A database from a newer build is refused at launch.** `migrate()` threw nothing when `user_version` was above the schema this build knows, so an older build opened a newer file and failed later with raw `no such column` errors — after possibly writing to a schema it did not understand. It now raises `SchemaTooNewError` before any window opens, the main process shows "This database is from a newer WageRoute" and exits, and the file is left untouched.
- **Updating a goal that no longer exists no longer writes a dangling pointer.** `updateGoal` called `updateRow` (a silent no-op for a missing row) and then bound funding accounts anyway, leaving `dedicated_goal_id` pointing at a goal that does not exist. The goal is now required before the transaction and the test asserts the account is untouched.
- **A goal's manual emergency target survives every other save.** Editing any setting used to write the manual target back from an empty draft, silently zeroing the number the user had entered; the manual target is now only written when manual mode is actually saved, and switching from automatic to manual restores the stored target instead of clearing it.
- **Closing a dialog no longer drops focus to the top of the window.** Focus returns to the button that opened the dialog, so the next Tab continues where the user was instead of restarting at the sidebar.
- **Tab can no longer reach the screen behind a dialog.** The trap wraps at both ends of the panel, and Shift+Tab from the first control lands on the last.
- **The allocator can no longer be dismissed mid-write.** It used to accept Escape and backdrop clicks while a route was committing; a dismissed write left the user with no confirmation that their paycheck had been recorded. Closing is now refused until the write finishes.
- **An error toast stays until it is read.** Previously every toast disappeared after 4.2 seconds, including a failed save the user had not finished reading; errors now persist and only successes expire. Hovering or focusing any toast pauses its timer.
- **A toast can no longer be dismissed by accident.** Clicking the message text used to dismiss it — including while selecting it to copy — and now only the close button does.
- **A bill due after the last guaranteed check no longer collapses to $0 per cheque.** An un-anchored bill whose due day lands outside the guaranteed slots (say, the 31st on biweekly pay) now spreads its monthly equivalent across the checks it will actually meet instead of reserving nothing; with a pay anchor set, the real checks carry it and an extra third check is surplus.
- **The ledger's month query uses its index again.** The rebuilt `idx_transactions_user_date` covers `(user_id, occurred_on)` for live rows, so listing a month no longer sorts a temporary B-tree on every snapshot (`PF-5`). The v7 migration asserts the plan in `EXPLAIN QUERY PLAN`.
- **Adopting the old Cash Flow Routing database is atomic and verified.** The copy is staged under temporary names, the SQLite header is checked before and after, the staged file must pass `PRAGMA quick_check` while opened read-only, and only then are the sidecars and the database renamed into place — so a crash mid-copy cannot leave a half-written or WAL-less database as the live one, and a failure leaves the original folder untouched and reports why. One unreadable legacy file used to be enough to poison the new install on every launch.
- **An unclosed quote in an imported CSV now fails with the line it starts on**, instead of folding every remaining row into one field and importing a truncated file without complaint.
- **An archived account cannot receive new money.** `requireAccount` has always returned archived rows, so a bill, a transfer or a paycheck could still post to an account that is hidden from every total and every picker. New entries, transfers, bill edits and paycheck deposits are now refused with *"That account is archived — restore it before using it here"*; editing a row that already sits on an archived account still works.
- **A row that is not a transfer cannot carry a destination account.** Ordinary expenses, bill payments and investments accepted a `counter_account_id` that nothing read, which is how the demo seed ended up with a decorative link. Only transfers may name a second account.
- **A round-up sweep's memo stays inside the column.** The composed `Round-up · …` text could exceed the 240-character limit that every other memo respects.
- **Only currency codes the platform actually knows are accepted.** `NumberFormat` happily prints `ZZZ`, so the shape test let any three capital letters through and the ledger kept a code that means nothing. Settings now fall back to USD for an unknown code and the importer reports the row instead of writing it.
- **Every snapshot is one read transaction.** `getSnapshot` ran eight statements separately, so a save landing between them could hand the UI figures from two different states of the ledger.
- **The demo seed no longer writes the savings transfer twice.** `createTransaction` writes both legs of a transfer, and the seed then wrote the savings side again, so the demo profile showed a savings balance $50 higher than the transfer it recorded. The investment pair keeps its two hand-written legs, now without the decorative counter-account.
- **CSV descriptions that a spreadsheet would run are defused.** A memo, account or category beginning with `=`, `+`, `-`, `@`, a tab or a carriage return is prefixed with an apostrophe on export, so `=HYPERLINK(…)` stays text, and the importer strips that guard apostrophe again so the file round-trips to the text it was. A memo that genuinely begins with an apostrophe keeps it. Amounts and dates are untouched.
- **A failed boot says so instead of showing nothing.** Anything thrown while the main process boots used to become an unhandled rejection: the app stayed running with no window, no dialog and no log. It now logs, shows "WageRoute could not start" with the reason, and quits.
- **Allocation reads are scoped to the user.** The goal-funded total and the per-paycheck allocation list now filter on `user_id` rather than trusting the parent row's scope alone.
- **The import guard measures bytes, and a reset drops held imports.** The size check compared UTF-16 length, so a file of multi-byte characters could pass a limit its bytes had already failed; and an import held between preview and confirm survived an erase, ready to confirm into the fresh profile.
- **A bare `$` is no longer read as zero dollars.** `parseMoneyToCents` returned `0` for an empty remainder after stripping a symbol, so `$`, `usd`, `-`, `.` and the contradictory `(-5)` all posted a $0.00 entry instead of being refused. Those now return null, while `USD 5`, `.5`, `+12.30` and `1,234` keep working.
- **A CSV error names the line in the file, not the row after the header.** Rows are now parsed as `{ line, cells }`, so a quoted newline in an earlier row no longer shifts every later line number by one; the entry importer, the mapping problems and the review grid all report the physical line.
- **One date order per imported file, and a warning when it cannot be proved.** A slashed date above 12 proves the order for the whole file, so a statement holding `31/12/2026` and `03/04/2026` reads both day-first instead of shifting one row by a month; a file whose slashed dates are all 12 or under is read month-first and the import says so up front, naming the first such date and asking for `YYYY-MM-DD` if it is day-first.
- **A CSV export keeps every entry's bank.** The institution column fell back to the first matching account in a filtered list, so exporting a ledger whose accounts were archived or filtered dropped the bank name; it now falls back to the institution joined onto the entry itself.
- **Imported text cannot create a row the app refuses to edit.** A memo over 240 characters, a category over 60, or control characters from a spreadsheet are stripped on import, and the row is reported as trimmed. One row that breaks a constraint is now reported against its line instead of aborting the whole file.
- **Editing or deleting a row that no longer exists says so.** `updateRow`, `softDelete` and `deleteTransaction` silently did nothing for a missing or already-deleted id, so the UI closed a dialog on a save that never happened; they now raise `RepositoryError('NOT_FOUND')`, and `deleteAccount` refuses an unknown account before it touches anything.
- **Scalar columns validate their type instead of coercing it.** A bill due day must be a whole number from 1 to 31 and anything else is refused rather than clamped (it used to round `NaN` and squeeze 99 into 31), a paycheck choice is the 1st through the 4th check (`0` used to be accepted and meant nothing), sort order must be numeric, and a flag column accepts only a boolean or `1`/`0` — the string `"false"` used to be truthy and switched the flag on.
- **A settings boolean stored as `1` or `0` keeps its meaning.** The importer stringifies a JSON boolean, so a restored backup read every `true` as `false`; `parseSettings` now accepts both spellings and falls back rather than guessing for anything else.
- **An account literally named `constructor` is not mistaken for a mapping.** The import wizard's account map is now null-prototype and consulted with `Object.hasOwn`, so a name that collides with `Object.prototype` maps normally and an unmapped row is still reported.
- **Deleting an account no longer rewrites rows that are already gone.** The bill, goal and paycheck pointers cleared by `deleteAccount` now carry `AND deleted_at IS NULL`, so a tombstone's `revision` and `updated_at` stay as they were.
- **A failed import says so in the wizard.** `runImport` used to resolve without a usable result, so the wizard could not tell the user what went wrong beyond a toast; it now returns the message, the review step prints it, and the text states that a failed import writes nothing.
- **A bill prompt that cannot be logged says why.** When no account can receive the payment, the row now prints *"Add an account before logging this payment"* instead of leaving a disabled button with a tooltip.
- **A bill pointing at an archived account cannot log a payment into it.** The prompt used the saved account id even after that account was archived, so **Yes, it cleared** would post money into a balance no total counts. The row is now blocked with *"The account this bill pays from is archived. Edit the bill to choose another one."*, and the bill dialog lists that pointer as a disabled `(archived)` option instead of displaying a different account while saving the old one.
- **Autopay no longer charges a bill twice.** `postDueAutopay` posted the full bill amount even when a part payment for the same cycle was already in the ledger, so a $120 bill with $50 logged would have a further $120 written at launch. It now posts only `amount − already matched`, exactly as the prompt card counts it, and the bill dialog's autopay hint describes what actually happens instead of the old *"WageRoute never posts a payment"*.
- **A transfer leg can no longer be edited to zero.** `updateTransaction` passed `allowZero` on an edited amount, so one half of a paired transfer could be set to `$0.00` while the other leg kept its figure, leaving a pair that no longer moves anything. The edit now raises the same *Amount cannot be zero* validation as the create path, the row keeps its previous amount, and the regression test asserts both halves.
- **A bill already paid is no longer withheld from Safe to Spend.** The Priority Wall is a smoothed monthly figure, and the dashboard deducted all of it even after a bill was paid, so the same money was taken from the pool twice. `unpaidMonthlyWallCents` now subtracts this calendar month's payments linked to each bill, clamped at zero, and `selectSafeToSpendCents` uses that figure; a weekly bill releases only the instance that was paid, a monthly one leaves the wall once settled, and a linked refund lowers the credit. The deduction row reads **Priority Wall / still unpaid** with *($X already paid)* beside it, while the wall's receipts keep reading **Reserved this month** and **Paid this month**.
- **A retried route cannot write the paycheck twice.** The allocator now mints one id per open draft and sends it with the commit; the id doubles as the paycheck row id, so a second submission of the same draft finds the row and returns it with `alreadyCommitted: true` instead of reserving the wall and recording the income again.
- **A transfer cannot point at a paycheck that no longer exists.** `createTransaction` accepted any `paycheckId` string, so a line could cite a deleted check and a plan move would never recognise it as settled. The repository now requires a live paycheck for the user before either leg is written.
- **The allocator stops withholding a bill it already paid this month.** Safe to Spend had already stopped deducting a settled bill, but the routing preview still reserved the full monthly figure, so payslips kept holding back money the ledger no longer owed. Bill reads now carry this month's payments per bill into `billFundingReserveCents`: a fully paid bill reserves nothing, a part payment reserves only the remainder, and the allocator's preview and the commit use the same figure.
- **Safe to Spend only counts the plan's own moves as settled.** `unsettledRoutingCents` treated *any* positive amount landing in a credit or investment account during the cycle as the routing having happened, so an unrelated card payment or a market deposit released money that was still sitting in checking. A move now also has to carry a paycheck id belonging to this month's checks — which every transfer `applyPaycheckPlan` writes does.
- **A restore cannot resurrect a setting this build deleted.** The importer checked only that a settings row had a key, so an old backup re-inserted keys no screen reads and every later export copied them forward again. A key this build does not know is now reported and skipped, settings the file does not carry stay as they were, and the allowlist itself is checked against the schema in the tests.
- **A kind cell that collides with an object member is not a kind.** `normalizeKind` read `KIND_ALIASES['constructor']` as a function and produced a `NaN` amount; the lookup now uses `Object.hasOwn`, so an unknown kind falls back to the sign of the amount.
- **The Priority Wall says whose share a column is.** Under **Per check** the table printed each bill's reserve for one check, which on a single-check strategy is the whole month; the column is now titled **Per check** with a tooltip stating that, and the summary reads **Average per check** when no pay anchor is set instead of claiming a per-check figure the strategies do not share.
- **The routing preview reads the pay date's month, not today's.** The allocator's reserve used this calendar month's bill payments while the commit withheld against the month of the date entered, so a cheque dated near a month boundary was previewed against the wrong month's payments — 13 November was released by a payment made 31 October. A new `bill:payments` channel answers one `YYYY-MM` month (and refuses anything else), and the allocator asks for the pay date's own month; if that read fails it holds the whole month rather than understating the wall.
- **"Erase all data" leaves no tenant table behind.** `wipeAllData` had never been given the two schema-8 tables, so an erase left every category and every `balance_snapshots` row in the file — the latter holding each account's daily balance. Both are in the wipe list, and a test asserts every tenant table counts zero afterwards.
- **A failed legacy adoption no longer opens a fresh ledger.** The dialog promised the old data was untouched, and boot then carried on and created a new database at the target path; the next launch skipped adoption because the target existed, stranding the old ledger for good. Boot now quits after the dialog and asks the user to fix the problem and open the app again.
- **A committed import is not reported as failed because the refresh failed.** Confirm commits and then re-reads the snapshot inside one `try`, so a read error produced an error toast even though every row had been written. The import is now reported, with *"reopen WageRoute to refresh the screen"* appended when the read did not come back.
- **A combined OFX file is refused instead of merged.** A QFX export can hold several statement blocks, and every line would have landed in the account picked for the first. The parser now refuses it: *"That file holds N statement accounts — export one account at a time"*.
- **Old Quicken two-digit years import.** `10/05'26` and `12/31'99` are expanded (70–99 → 19xx, everything else 20xx) instead of failing the date and dropping the row.
- **A transfer-only QIF says what it held.** The refusal used to claim the file had no transactions; it now carries its first issue — *"no importable cash transactions — statement line 2 is a transfer"*.
- **A CSV alias that contradicts its amount is reported.** A canonical kind decides the sign silently by design (`expense,42.50` → −42.50), but an alias is a weaker claim: `Payment,500` now imports as an expense and the wizard says *"row N says “Payment” but its amount is positive; imported as expense — check the sign"*.
- **A bill paid on a card stays withheld from Safe to Spend.** The wall treated every bill payment as money that left the pool; a card payment left the pool untouched and raised the debt instead. The month totals now carry `creditCents` from the paying account's kind, and the deduction releases only the spendable part, so a cash payment clears its bill and a card payment keeps it withheld.
- **A card close day past month end steps back inside the month.** `previousCloseDate` used plain month arithmetic, so a close day of the 31st read 28 January when asked from February and counted the last days of January against the wrong statement; it now clamps per month and answers 31 January.
- **A dialog saves once, however fast Enter repeats.** `useDialogSave` relied on the re-rendered `disabled` attribute, which a held Enter key can outrun; an in-flight guard now ignores every submission until the first write finishes.
- **A bill on an archived account can still be edited.** The form sends the saved account id back and validation ran on it, so archiving an account trapped every other field of a bill pointing at it. Only a different destination is validated now.
- **An overpaid card keeps its credit.** The Adjust Balance dialog started from `Math.max(0, owed)`, so a card carrying a credit silently began at zero and the first save wiped the credit; a shared `cardOwedCents` keeps the sign and the hint reads *"Credit on the card: $X"*. **Pay card** says *"The card is overpaid by $X"* and, with no spendable account, disables the button and names the kinds to add instead of offering a dead end.
- **A rejected grid edit snaps back.** A save the repository refused left the edited cell showing a value that was never stored; the grid now re-reads on failure, as the confirmed-edit path already did.
- **Sorting the ledger clears the row selection.** The ticks survived a sort, so a bulk delete after reordering could remove rows the user had never chosen; a sort change and a page clamp both clear the selection.
- **The Windows installer builds again.** NSIS reads `installerIcon` itself and does not convert a PNG, so `build/icon.png` failed `makensis` with *invalid icon file* and the tag build stopped before the MSI smoke test. `build/icon.ico` now carries the same artwork at 16–256 px and NSIS loads that.

### Removed

- **Four unused exports** — `advanceByFrequency`, `sumCents`, `safeCents` and `leisurePercent` — are deleted from `src/shared`. Each had been superseded (`advanceByFrequency` by the occurrence engine) and none was called.
- **Dead plumbing** — the unused `@renderer` alias in `electron.vite.config.ts` and `tsconfig.json`, two unused type imports in `repositories.ts`, a dead string local in `importRepair.ts`, and a duplicate `dist:linux` script in `package.json`.
- **Three settings rows no released build ever read** — `emergencyAccountIds`, `insurance_floor_cents` and `round_up_enabled` — are deleted by the v7 migration. The live round-up switch is `roundUpEnabled` and is untouched; only the draft keys that [ADR 0009](docs/decisions/0009-the-goal-chooses-its-funding-accounts.md) documents as never writable are cleaned up.

## [1.1.0] - 2026-10-29

Tag `v1.1.0`. Schema **3 → 4 → 5 → 6**; backups written at version 6, versions 2–6 accepted. Installers: `WageRoute-1.1.0-arm64.dmg`, `WageRoute-1.1.0.dmg` (Intel), `WageRoute.Setup.1.1.0.exe`.

This is a minor release because every schema migration is at least a minor bump ([semver policy](docs/RELEASING.md#semver-policy)). Everything in this section merged after `v1.0.2` (`7fce57b`) and had no installer before it: the import wizard as PR #12 (`8b25329`), dedicated accounts (schema 4) as PR #13 (`76283d4`), bill funding strategies, goal-owned funders and account colours (schema 5) as PR #16 (`100bc65`), and the last-check, pay-cycle and split-cap work (schema 6) as PR #18 (`ec07dae`).

### Added

- **"Last check of every month" — the fifth funding option** — a bill can now put the month's obligation on the last check the pay cycle is *guaranteed* to have: the 1st on monthly pay, the 2nd on semimonthly and biweekly, the 4th on weekly. A biweekly month with a third check still funds on the second, because a slot that disappears in a short month would leave the bill unreserved — the same rule that already bounds the "Which paycheck?" list. The option sits fifth, after the owner's original four, so the numbering they asked for is unchanged, and the dialog hint says "the last check your pay cycle is guaranteed to have every month" rather than leaving it to be discovered. [ADR 0011](docs/decisions/0011-the-pay-cycle-is-a-setting.md) records the semantics and what it costs.
- **The pay cycle is a setting, with a payday label** — a new Settings → **Paycheck** card edits the pay cadence, a free-text **Payday label** (`15th and last day`) and the **Default paycheck account**. The cadence was previously editable only inside the allocator's step 1; it is the same stored key, so moving the editor does not fork the value. The label is display only — it appears next to the cadence on the wall ("Biweekly pay cycle · 15th and last day · averaged") and in the allocator's step-1 hint — and is deliberately not parsed into dates, because a wrong parse would move money silently while a caption cannot.
- **Default paycheck account** — the allocator preselects the account chosen in Settings, falling back to the first non-archived checking account and then the first non-archived account, so an archived or deleted pointer degrades to the old behaviour instead of blocking a paycheck.
- **Database schema version 6** — a rebuild of `bills` to widen the `funding_strategy` CHECK to include `last_check`. No column is added and no default changes, so an upgraded database moves no number and every stored strategy stays what it was. The rebuild is the second of its kind (migration 2 rebuilt `allocations`) but the first on a table the ledger references, and it needed `PRAGMA legacy_alter_table = ON` *plus* suspended foreign keys — both set outside the transaction, where they are not no-ops — or SQLite rewrites `transactions.bill_id REFERENCES bills(id)` during the rename and the migration fails. `migrate()` now runs `PRAGMA foreign_key_check` inside the transaction and throws on a violation, so a bad copy rolls back instead of committing a broken ledger. Verified against a **copy** of the live version-5 database: `user_version` 5→6, all counts identical (12 accounts, 4 bills, 3 goals, 25 transactions, 2 paychecks, 19 settings), `integrity_check` ok, no `foreign_key_check` violations, enforcement and `legacy_alter_table` restored, `transactions.bill_id` still pointing at `bills`, and a `last_check` write accepted then reverted.
- **`src/main/db/migrations.test.ts`** — a new file covering the v6 rebuild end to end: v5 rejects `last_check`, v6 accepts it and still rejects `sometimes`, rows/defaults/`idx_bills_sync` survive, a referenced bill still cannot be deleted, enforcement is restored afterwards, and a pre-seeded dangling `bill_id` makes `migrate()` throw, roll back to version 5 and leave `bills` un-widened. `npm test` is now **73 tests across eight files**.
- **`cadence.test.ts` grew a fifth strategy** — the last slot per cadence, "a bill on the last check reserves there and nowhere else" (0 / $1,200 / 0 across a three-check biweekly month), and the month-total invariant now loops over all five strategies.

- **Which paycheck pays a bill — four options** — a bill now declares how its reserve is collected, in the order the owner asked for: **1. Closest to the due date**, **2. A specific paycheck** (chosen from a "Which paycheck?" dropdown), **3. Reserve from all paychecks** (the old spread, still the default), **4. First check of every month**. The three single-check strategies move the **whole month's** obligation onto one identified paycheck and reserve nothing on the others, so summing a month gives the same figure whichever option is picked — now an asserted property, not a hope. The wall row of a single-check bill prints the monthly figure under the per-paycheck column with a **"Nth check only"** sub-label, and the bill dialog shows a live derived line ("Reserves the whole month's obligation on the 2nd paycheck, closest to the due day"). [ADR 0008](docs/decisions/0008-one-check-carries-the-month.md) records the model change, the slot approximation it depends on, and what it costs.
- **The goal chooses its funding accounts, one or several** — the set of accounts behind a goal's progress is edited **on the goal**, in a **Funded by** picker: a dropdown for the common single-account case, and a **"Let several accounts add up together"** checkbox that swaps it for a tick list. An account already funding a different goal is labelled `(funds That Goal)`, so taking it is visible rather than a silent steal. Goal row and every binder commit in **one transaction** — a failed binding rolls the whole save back. [ADR 0009](docs/decisions/0009-the-goal-chooses-its-funding-accounts.md) records why the relation moved off settings and why one account still funds only one goal.
- **Pause saving towards the emergency fund** — an **active** switch on the emergency card. Paused reads *"Saving paused"* with a *"Resume saving"* action, and `commitPaycheck` drops the emergency goal from the plan before the allocator runs, so no *Route* button appears for money that will not be routed and its share falls through to savings. Other goals keep their own cadence: pausing the emergency fund pauses one goal, not sinking funds. The copy never says *bill*, because this is a goal.
- **Account colours** — each account can carry its own colour (eight swatches plus **Automatic colour**, which falls back to the account type), shown as the dot on the account row and wherever the account is named.
- **Database schema version 5** (`bills.funding_strategy`, `bills.funding_paycheck_index`, `accounts.color`) — additive: one `NOT NULL DEFAULT 'all_checks'` column, one nullable integer, one nullable colour. Every released bill lands on `all_checks`, which is arithmetically identical to the pre-v5 rule, so upgrading a database moves **no number**. Migration verified against a **copy** of the live version-4 database: `user_version` 4→5, all three columns present, defaults applied, `integrity_check` ok, row counts unchanged.
- **`src/shared/cadence.ts` under test** — a new file, `src/shared/cadence.test.ts`, covering slot placement for all four cadences, the tie-break rule, the guaranteed-slot clamp, the $50-weekly → $216.67 figure, the no-clock fallback, and the month-total invariant for every strategy. `npm test` is now **68 tests across seven files**.
- **Backup compatibility for the three new columns** — they are in the importer's allowlist (export is `SELECT *`, so a column missing from the allowlist would silently vanish on import); `bills.funding_strategy` also needed an entry in `TABLE_DEFAULTS`, because a `NOT NULL` column omitted by an older backup otherwise inserts an explicit `NULL` — the same class of crash as `2024f7f`, caught by the test rather than by a user.
- **Import wizard: ask instead of failing** — `8b25329` (#12, [ADR 0006](docs/decisions/0006-import-wizard-asks-instead-of-failing.md)). Importing a JSON backup or a CSV entries file now runs in two IPC steps. `data:preview` parses the file, keeps it in the main process behind a single-use token, and returns one question per unusable field — a missing name, an enum typed `chekcing`, a `due_day` of 45, a posting account that does not exist, a CSV bank label matching no local account. `data:confirm` re-derives the same questions from the shared rules, applies the answers and merges only the rows that survive. Every row can be fixed with its own editor (text, amount, whole number, date, dropdown of accepted values, dropdown of local rows plus **Leave unlinked**) or left out, and a left-out row is listed with every reason on it and how to repair the source file. An answer that still fails validation drops that row with the validator's message rather than throwing.
  Detection lives in pure shared code (`findImportProblems`), so the questions the wizard showed and the questions the importer checks are the same function, and the answer keys are safe across the two calls.
- **Account purposes: "this account is only for this"** — dedicated accounts. An account can now be bound to one sinking fund, and **that account's balance *is* the goal's progress**: no claim step, no separate top-up ledger. A goal funded this way shows the account name on its card, and the allocator stops routing paychecks into it because the money is already where it belongs. [ADR 0007](docs/decisions/0007-dedicated-accounts-balance-is-progress.md) records the decision, the alternative that was rejected, and what it costs.
- **Per-account Safe-to-spend choice** — each account declares whether it counts as spendable money, chosen at creation and editable afterwards: *Automatic* (checking, savings and cash count; investment and credit do not), *Always count it*, or *Never count it*. Investment accounts are excluded by default, which was the recommendation.
- **Total wealth** — one number for everything owned: cash, money parked in dedicated goal accounts and investments, minus credit owed. It appears as a strip on the Overview page with a bucket breakdown (*Cash · Saved for goals · Invested · Credit owed*), as the first summary tile on Accounts, and as a second line in the sidebar stat. Every surface calls the same `totalWealthCents`, so they cannot drift apart. Motivation was explicit: a small spendable balance read as poverty while goal and investment money existed uncounted.
- **Database schema version 4** (`accounts.dedicated_goal_id`, `accounts.in_safe_to_spend`) — additive, both columns nullable, plus a partial index on the goal pointer. Migration verified against a **copy** of a live version-3 database: `user_version` 3→4, both columns present, index created, `integrity_check` ok, no `foreign_key_check` violations, and all rows preserved (11 accounts, 14 transactions, 3 goals, 3 bills, 17 settings). No existing row opts in, so behaviour for an upgraded database is unchanged until the user chooses.
- **Backup compatibility for both new columns** — they are in the importer's allowlist (export is `SELECT *`, so a column missing from the allowlist would silently vanish on import), askable by the wizard when a pointer dangles, round-trip tested, and present in `examples/backup.example.json`.
- **Seven new shared rules under test** — `src/shared/accounts.ts` plus 15 new tests: explicit choice beats the kind default, a dedicated account is not spendable unless forced, archived accounts count for nothing, the pool is not all cash, credit subtracts from wealth, the buckets partition total wealth exactly, goal money outside the pool is not deducted from it, and the allocator skips account-funded goals. `npm test` stood at 56 tests across six files when this landed; the schema-5 entry above raises it to 68 across seven.

### Changed

- **The pay cycle left the allocator.** `payCadence` used to be written only when a paycheck was routed, so the wall's cadence could not be changed without routing one. It is now edited in Settings → Paycheck alongside the new payday label and default deposit account; the allocator still shows it and still saves it on commit, so a route started from an old habit keeps working.
- **The split controls cap each other at 100%.** Each of the four percentages is capped at 100 minus the other three: with debt at 90 the other sliders stop at 10, and typing 100 into savings snaps to 10. Space freed by lowering one bucket is immediately available to the others. The allocator's largest-remainder scaling and the "Splits exceed 100%" guard remain, but now cover state the UI cannot create — settings imported or hand-written above 100 — rather than a number the user just typed.
- **A goal's funders are edited on the goal.** The account dialog's "Mine only for" pointer still exists and writes the same column, but the goal screen is now the place to see and change the whole set, including releasing all but one in a single save. `settings.emergencyAccountIds` was deleted; the settings table keeps ignoring any draft row that used it. [ADR 0009](docs/decisions/0009-the-goal-chooses-its-funding-accounts.md).
- **The wall and the allocator are date- and strategy-aware.** `buildAllocationPlan` and the wall's per-paycheck column both call `billFundingReserveCents(bill, cadence, paycheckDate)`; a bill whose reserve lands on one check contributes 0 to the others, and `all_checks` reproduces the old spread exactly. The wizard's step-2 total therefore depends on the pay date entered in step 1, which is the intended behaviour and is stated in [FEATURES.md](docs/FEATURES.md).
- **The emergency card says "goal", not "bill".** Paused state reads *"Saving paused"* with *"Resume saving"*, matching the wall's inactive-bill behaviour without borrowing its noun.
- **Safe to Spend is measured against the spendable pool, not all cash.** The formula is `spendable pool − monthly Priority Wall − the funded goals whose money is in that pool` instead of `cash on hand − …`. The committed-spending meter still uses cash on hand deliberately; only the hero number changed. The old documentation called the double count "by design" — it was not.
- **Fixed: dedicated-account goal money was deducted twice.** The first cut of the pool excluded a dedicated account from the pool *and* still subtracted its balance as goal progress, so a profile with $1,200 in checking, $4,200 in a dedicated savings account and no bills reported Safe to Spend as **−$3,000** instead of $1,200. Found by driving the built app over the Chrome DevTools Protocol, not by reading the code. `poolEarmarkedGoalsCents` now deducts only allocation-funded goals, and the hero's breakdown rows are labelled "Spendable accounts" and "Funded goals from the pool" so the arithmetic shown actually adds up. Excluding dedicated money from the pool is still only a **default**: choosing *Always count it* on a dedicated account reproduces the double count on purpose, which is the user's call, not a bug.
- **Goal progress has two sources.** Allocation rows for ordinary goals; the bound account's balance for dedicated ones. The balance *replaces* allocation rows rather than adding to them, so routing a paycheck into a dedicated account's goal cannot double-count. Deleting the goal detaches the pointer instead of deleting the account, and archiving the account hands progress back to the allocations.
- **`docs/SECURITY.md`: an unusable row no longer aborts an import.** The threat model previously claimed a constraint failure rolls the whole transaction back. Rows are now caught individually and the rest commit, which is stated with the change that made it true.
- **Documentation reconciled with the code.** `README.md`, `docs/DATA-MODEL.md`, `docs/FEATURES.md`, `docs/IMPORT-EXPORT.md`, `docs/DEVELOPMENT.md` and `docs/ARCHITECTURE.md` moved from schema version 3 to 4 and from app version 1.0.1 to 1.0.2; the Safe-to-Spend formula, the module map (the real `src/shared` file list), the migration recipe (including why a pointer that closes a foreign-key cycle must be validated in code, not declared), and the backup version-acceptance table all now match what ships. `docs/DEPLOYMENT.md` no longer says the working directory "is not currently a git repository". The schema-5 work moves the same set to version 5 / backup 5 / accepted `2`–`5`, adds [ADR 0008](docs/decisions/0008-one-check-carries-the-month.md) and [ADR 0009](docs/decisions/0009-the-goal-chooses-its-funding-accounts.md), documents the four funding strategies and the shared cadence module in `ARCHITECTURE.md`, and records the `TABLE_DEFAULTS` requirement for a `NOT NULL` column in `DEVELOPMENT.md`. The schema-6 work moves them again to version 6 / backup 6 / accepted `2`–`6`, adds [ADR 0011](docs/decisions/0011-the-pay-cycle-is-a-setting.md) and the fifth strategy, documents the Paycheck card and the split cap in `FEATURES.md`, the two new settings keys and the `last_check` row in `DATA-MODEL.md`, and the `legacy_alter_table` rebuild recipe in `DEVELOPMENT.md`.
- **Release documentation retargeted.** `docs/RELEASING.md`'s worked example is now the queued 1.1.0 release rather than a hypothetical `0.2.0`, its version table shows the working-tree schema, and the installer names in the docs carry 1.0.2 asset names. The `curl` install block's DMG volume path was verified by mounting a released DMG rather than guessed.

### Fixed

- **A bill set to "Last check of every month" silently kept its old strategy.** The repository's `BILL_FUNDING_STRATEGIES` allowlist was not widened with the enum, so `createBill`/`updateBill` rejected the value before SQLite's CHECK ever saw it: the dialog closed, the row still read "1st check only", and the database still held the previous strategy. Found by driving the built app over CDP, not by the test suite — the new migration test exercised the database CHECK and said nothing about the IPC boundary that guards it. Fixed and re-verified: the row now reads "2nd check only" and the stored strategy is `last_check`.

### Known gaps

- **The phone's editors have not been driven on a handset.** Bills, goals, accounts and entries were each added, edited, archived and deleted through the Chrome DevTools Protocol against the built shell, with IndexedDB read back directly; every sheet, refusal, delete question and persisted row checks out. But no real phone has installed the shell, opened it with the network off, or carried a file through its own share sheet. GitHub Pages is still not enabled.
- **The edge shape has met a stub, not a provider or a phone.** The `edge` profile was validated and driven end to end behind Caddy, but the identity provider in that test was a container answering 200 for one cookie value and 401 for everything else: no Authelia, Authentik or basic-auth realm has completed a real login in front of these images, no handset has resolved a name in this shape or had the CA installed. Two tenants have since run side by side and their separation was measured rather than argued (2026-11-04, `arm64`, ~205 MiB per extra person idle), but no second **physical** machine on the operator's own network has ever tried to reach a tenant's address, and passkeys stay unproven by construction — WebAuthn wants a registrable domain as its `rpId`, and a `.lan` name is not one.
- **The schema-6 surfaces were driven in the built app, and the walk found a real defect.** Over CDP against a disposable profile built from a copy of the migrated live database: the Settings → Paycheck card (cadence select, payday label committed on a real `focusout`, default account select) surviving a round trip through IPC into SQLite; the wall's summary hint reading "Biweekly pay cycle · 15th and last day · averaged"; the five numbered funding options and the `last_check` hint; a row reading "2nd check only"; the allocator preselecting the configured default account and showing the payday hint in step 1; and the split cap — with debt at 90, typing 100 into savings snapped to 10, both inputs carried `max=10`, and the summary read "Routed 100% of the True Surplus / 0% stays guilt-free". The walk is how the `last_check` write-path bug under **Fixed** was found. Screenshot capture and assistive access remain denied, so appearance is still unverified and no component test re-runs any of this.
- **The new UI has now been driven in a running app.** Launched built arm64 bundles against a disposable profile (`CFFIXED_USER_HOME=/tmp/...`) with `--remote-debugging-port`, and walked every new surface through the Chrome DevTools Protocol: the first-run card, the account create and edit dialogs with both new controls and their conditional hints, the row badges, the Total wealth tile and strip, the goal card's progress and funding-source chip, and the tri-state safe-to-spend choice surviving a round trip through IPC into SQLite and back (the badge disappears with *Always count it* and returns with *Automatic*). This is how the −$3,000 double deduction under **Fixed** was found — type-check and the test suite were green while the composed number was wrong. Screenshot capture and assistive access remain denied on this machine, so the *appearance* is still unverified even though the *behaviour* is. No component tests exist; the verification was manual and will not re-run itself.
- **The schema-5 surfaces were driven in the built app too, and the walk found real defects.** Over CDP against a disposable profile: the four numbered funding options in the bill dialog and their derived hint, the "Which paycheck?" field appearing only for cadences with more than one slot, the wall's "Nth check only" row, the **Funded by** dropdown and its **"Let several accounts add up together"** tick list (including `(funds That Goal)` and the empty state), the goal card's per-account balance list, and the eight colour swatches plus **Automatic colour**. The walk caught a picker still labelled **"Held in"** while writing `fundingAccountIds` — relabelled **"Funded by"** with an accurate hint — and verified that the wizard's step-2 total matches the chosen strategy to the cent. Screenshot capture and assistive access remain denied, so appearance is still unverified and no component test re-runs any of this.
- **The import wizard's rendered flow is still not driven.** Its detection and repair rules are tested as pure code, but the wizard opens a native file picker that the DevTools Protocol cannot reach, so opening a file from the dialog by hand is still somebody's job.
- **Only the arm64 macOS installer has been launched.** The 1.1.0 arm64 DMG was mounted, its volume name confirmed, and the bundled app run from `release/mac-arm64` against a disposable profile built from a **copy** of the live database: it migrated that copy 5→6 with identical counts, a clean `integrity_check`, no foreign-key violations and the same wall figures ($492.69 due / $227.40 set aside). The x64 DMG builds and reports the right version but has never been started, and the Windows installer is produced by CI and has never been run by anyone.
- **1.1.0 was installed over the app after publication.** The release was verified against a **copy** of the live schema-5 database; the owner then approved the irreversible install. On 2026-10-29 the live `wageroute.db` was snapshotted with `sqlite3 .backup` into `.local-backups/2026-10-29-pre-1.1.0-install/` (schema 5, 12 accounts, 4 bills, 3 goals, 25 transactions, 2 paychecks, 19 settings, `integrity_check` ok), the old schema-5 bundle was **moved, not deleted**, to `.local-quarantine/2026-10-29-pre-1.1.0-install/WageRoute-1.0.2.app`, and the app was copied out of the published arm64 DMG. First launch migrated the live ledger to `user_version` **6** with every count unchanged, `integrity_check` ok, no `foreign_key_check` violations, the stored strategies intact (3 `closest_due_date`, 1 `all_checks`), and the wall still reading **$492.69** per month / **$227.40** per paycheck. There is still no downgrade path, so that snapshot is the only way back.
- **v5 and v6 backups are refused by older builds.** The backup format version rises with the schema, so a file exported from 1.1.0 cannot be imported by 1.0.2 (or by a build carrying only schema 4 or 5). There is no downgrade path for a version-6 database.
- **A single-check strategy can exceed the paycheck that carries it.** Under *Closest to the due date*, *A specific paycheck*, *First check of every month* or *Last check of every month*, one check may be asked for several bills' whole-month obligations at once. That is the point of the option, but it turns a previously covered wall into a visible shortfall on that date; the allocator reports the shortfall rather than smoothing it.
- **`last_check` is not "the last cheque I got".** In a biweekly month with three checks, a bill on `last_check` funds on the second, so a user reading the label literally is surprised once a quarter. The alternative — funding on the third check — would leave the bill unreserved in every two-check month, which the reserve model cannot allow; the dialog hint states the rule in words.
- **A dedicated account's progress can fall silently.** Spending from it lowers the goal with no warning; that is the point of "the balance is the progress", and it is the trade-off ADR 0007 accepts.
- **The Windows and Linux installers are CI-proven, not human-proven.** The MSI installs, launches, survives a reinstall and uninstalls on `windows-latest`; the AppImage and the extracted deb create their ledger under `xvfb-run` on native Ubuntu runners. The NSIS installer, the portable exe, the zip and the rpm are built but have never been launched by a person, and no Windows or Linux artifact has been opened on a desktop. All of them are unsigned, so the OS cannot vouch for the binary and the published `SHA256SUMS` is the only integrity check.
- **Nothing has been validated with a screen reader.** The focus trap, skip link, live-region toasts and labelled dialogs are exercised by keyboard over CDP, but no automated test asserts the focus behaviour and no assistive technology has been run against the app.
- **The installed app is not this tree.** `main` carries schema 8 and the migration writes a pre-upgrade copy, but `/Applications/WageRoute.app` is still the 2026-10-29 `1.2.0-dev` bundle at schema 6; installing the next build will migrate the owner's live ledger 6 → 7 → 8 on first launch. Snapshot the database before that install, as the 1.1.0 install did.
