# 0027 — One expansion answers every destructive question

**Status:** Accepted (2026-11-03)

## Context

[ADR 0026](0026-a-delete-confirmation-counts-the-rows-that-leave.md) fixed the entry question: before deleting ledger rows, ask the database how many really leave, and say it in one sentence both devices share. It left the rest of the product untouched, and the same failure was waiting in the other three destructive dialogs.

An **account** is the worst case, because the rows it loses are not all inside it. Deleting the chequing account of a $30.00 transfer retires that leg *and* the twin in savings; deleting the account a rounded-up purchase was made from retires the purchase *and* its two sweep legs, which live in the fund account. The desktop's dialog counted `accountEntryCount` — rows recorded in the account — so it promised 3 and removed 5. Worse, its writer walked transfer groups by hand and never looked for sweeps, which left a live sweep row pointing at a tombstoned purchase: a dangling link no read model can explain, and the phone — which already expanded through `expandDeletion` — removed different rows from the same file than the desktop did. Two devices, one ledger, two answers.

A **bill** deletes its set-asides and releases the entries recorded against it. The desktop asked with a hand-written sentence and no numbers at all; the phone counted a `payments` figure that included adjustment rows and then called them *payments … as ordinary expenses*, describing a write that does not happen — the entries stay, only their link goes.

The two **whole-ledger** questions named nothing. The desktop's erase dialog emptied accounts, bills, goals, paychecks and every entry and asked *Erase all data?* with no size. The phone's forget sheet did the same, and `docs/FEATURES.md` had long claimed it "counts what would be lost" — a documented behaviour the code never had. On that device the honest number was available for free: `Snapshot` carries `transactionTotal`, and the store keeps `localIds`, the live rows this phone wrote itself.

## Decision

**One expansion, one summary per shape, one module for the words — and a question never states a number the write will not agree with.**

1. **`doomedAccountDeletionIds` is the account's expansion, and it is the write.** `src/main/db/repo/transactions.ts` takes the account's own live ids and pushes them through the `doomedDeletionIds` walk ADR 0026 established. `deleteAccount` tombstones exactly that set and derives the bills whose reserves need reconciling from it, so the promise, the cascade and the twin/sweep handling are one computation. The hand-written transfer-group loop is gone; both devices now retire the same rows from the same file. The phone mirrors it with `doomedAccountEntryIds` over its in-memory tables.
2. **A bill's summary names both fates.** `BillDeletionSummary` is `{ reserves, linkedEntries }`: what goes with the bill and what stays without it. `linkedEntries` replaced `payments` because the count includes any live row carrying the `bill_id`, adjustments among them — a field may not call them something they are not. Both numbers are read with the same `WHERE` the write uses.
3. **Reads cross the wire; a read with no floor returns `null`.** `account:count-deletion` and `bill:count-deletion` join `transaction:count-deletion` as the contract's only read-before-write channels, all three answered by the process that owns the ledger and queued behind the writes the screen already made. ADR 0026 could fall back to the size of the selection, which is a proven lower bound. An account delete has no such bound visible to the screen — doomed rows can all sit in other accounts — so a failed read returns `null` and the shared wording admits not knowing rather than naming a number it cannot check. The same reasoning covers the read that has not landed yet: while it is in flight the desktop's account dialog shows *Counting what this removes…* with a disabled **Counting…** button, because the read-failed sentence — which promises *every* linked row — belongs to a measured failure, not to a pending measurement.
4. **Whole-ledger questions count from the snapshot.** `eraseAllWords` is built from `transactionTotal` and `paycheckTotal` — true database totals, not the grid's 500-row window — plus the arrays the snapshot already carries in full. `phoneCopyWords` separates the entries that live in this browser from the subset this phone wrote, and asks the person to export before forgetting if any of them has not reached the computer yet. It does not claim the computer has never seen them: `localIds` records what this device wrote, and a row that travelled back in a later export stays in it, so no number on the phone can tell the two apart. Neither sentence needed a new channel: the data was already on the device, unstated.
5. **`src/shared/deletion.ts` holds all six questions and the hint they share.** `entryDeletionWords`, `accountDeletionWords`, `billDeletionWords`, `goalDeletionWords`, `eraseAllWords`, `phoneCopyWords`, plus `archiveVsDeleteHint` — the one line the account question prints above them, which both devices had been typing by hand. A screen may add a device fact to a body — the phone still names the row's amount and the file it leaves through — and neighbouring helper copy on those screens (the erase flow's second step, the phone's danger-zone explainer) stays where it is, because it explains rather than asks. What may not happen again is a screen writing the question itself.
6. **A read the screens stopped using is removed.** `account:entry-count` survived the account dialog moving to `countAccountDeletion` as an unreachable channel with a live handler, preload method, `FinanceApi` entry and store action. It is deleted from the wire; `accountEntryCount` stays as an internal repository read that `deleteAccount` and the guards' tests still use. Dead IPC is not a compatibility layer, and `src/preload/api.test.ts` counts methods off `CHANNELS`, so the contract stays self-checking.

## Consequences

- Deleting a chequing account that holds a transfer leg and a rounded-up purchase asks *Remove Chequing?* above *Deleting removes the account and 5 entries from every total.* with a **Delete account and 5 entries** button, and the five go. Both devices agree, and no live sweep is left pointing at a retired purchase — pinned by `ledger-guards.test.ts` and `pocket/lib/write.test.ts` respectively. Measured in the running app on a disposable ledger: an account holding 20 of 24 live rows, whose transfer twin sits in savings, whose other transfer twin sits in cash and whose purchase sweep leg sits in the fund, asked with **23** and left exactly one live row behind — no half-transfer and no sweep pointing at a retired purchase.
- Deleting a bill with two set-asides and three linked rows reads *Its 2 set-asides go with it, and its 3 entries recorded against it stay in the ledger without the bill.*; the erase names how many entries, accounts, bills, goals and paychecks it empties; the phone's forget names how many entries leave the browser and how many of them this phone wrote, and sends the person to export before answering for the rest.
- The desktop's account and bill questions can fall back to a sentence with no number in it, while the entry question can still print a floor. That asymmetry is deliberate and stated in the shared wording, not smoothed over with a guess.
- `docs/FEATURES.md` had to be corrected rather than extended: it claimed an account delete leaves transactions in place showing the account name, which has not been true since the dialog started deleting them, and it claimed a counted forget confirmation that did not exist.
- Every future destructive action follows the same three rules: reuse the expansion, read the number from the process that owns the rows, and take the sentence from the shared module.
